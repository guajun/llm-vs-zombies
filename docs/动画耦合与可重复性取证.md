# 动画耦合与可重复性取证

日期：2026-09-20。范围：回答"可重复性是不是不需要动画级一致，只要阵型运转可重复"这一问。

方法：候选反编译源码静态阅读（固定提交 `8a2d121899ba5cb4df644cd7d2e4c1aaf88dd238`，本地副本在 `work/replay-research/`）＋ 现有真实 audit 档的差分量化。不启动游戏，不修改任何运行目录。每条结论标注证据强度：

- **[V]** 本项目对目标二进制（引擎 SHA-256 `f9669af3…1322`）的机器码或运行结果已直接验证；
- **[D]** 来自候选反编译源码，与已核实 RVA 一致，但未逐条独立反汇编；
- **[M]** 本次在真实 audit 档上实测统计；
- **[I]** 推断，未验证。

## 0. 结论摘要

1. **"动画"要拆成两层看。** 渲染派生层（overlay 矩阵、附加色、轨道插值标量、帧索引）确实不参与模拟，实测占每 tick 差分体积约 13%，可以从严格相等判据里剔除。**[M]**
2. **动画时钟层不能剔除。** 本引擎把 reanimation 播放进度当玩法时钟用：巨人僵尸的锤击判定就是 `ShouldTriggerTimedEvent(0.64f)`，命中即压掉那一格植物。这一层占差分体积约 25%，剔除它等于放弃玩法可重复。**[V][D]**
3. **动画创建消耗共享 RNG。** 新建 body 动画会调用 `Rand(4)` / `RandRangeFloat`，也就是动画对象的数量与顺序会平移全局 MT 流。表现层的差异因此存在一条放大回模拟的反馈通道。**[D]**
4. **动画时机是本项目里最精度敏感的量。** `mAnimTime` 是逐帧浮点累加（`+= 0.01f * rate / frameCount`）：24 位 x87 与 53 位累加会在长局里漂移，最终翻转 `0.64` 这类阈值。048 的实测差异字段里就包含 anim rate 与 `anim_time`/`last_frame_time`。**[V]**
5. 因此"阵型级可重复"要成立，代价不在"少存状态"，而在**改耦合**：把表现层随机拆成独立流、把玩法事件从动画阈值改为 tick 计数。这就是"改原版一部分代码"的正当用法，但必须显式标注 `original_engine_bitwise_unmodified=false`，并重新证明改后行为。**[I]**

## 1. 证据 A：动画时钟就是玩法时钟

### 1.1 积分器

```
Reanimator.cpp:408   mAnimTime += SECONDS_PER_UPDATE * mAnimRate / mFrameCount;
Reanimator.h:31      constexpr const double SECONDS_PER_UPDATE = 0.01f;
```

动画进度不按墙钟走，而是按**固定 10 ms 步长**累加。两个直接后果：动画在给定 tick 序列下本身是确定性的；同时它是纯浮点累加，误差沿长局累积（见 §3）。**[D]**

### 1.2 事件判定用区间包含

```
Reanimator.cpp:1248-1254  (ShouldTriggerTimedEvent)
    if (mFrameCount == 0 || mLastFrameTime <= 0.0f || mAnimRate <= 0.0f) return false;
    if (mAnimTime >= mLastFrameTime) return t >= mLastFrameTime && t < mAnimTime;
    else                             return t >= mLastFrameTime || t < mAnimTime;
```

即判断"本 tick 的播放区间是否跨过 `t`"。它天生对一帧误差敏感：时钟晚/早一个 tick，事件就晚/早一个 tick 触发。**[D]**

### 1.3 谁在读它（选摘）

| `Zombie::UpdateZombiePolevaulter` 行 1695 | `mAnimTime > 0.6f && <= 0.7f` | 决定撑杆跳是否结束、改写 `mPosX` 与 `mZombiePhase` | **[D]** |

真实事故先例 **[V]**：隐藏引擎长局 `017` 在 tick 4166 暴露缺口——红眼僵尸槽 45 锤击 phase 70、动画前次/当前进度约 `0.6399995/0.6424237`，原版按 `0.64` 触发 `SquishAllInSquare`，下一帧植物槽 65 的 `mSquished(+0x142)` 置位、`+0x4C=500`。修复后的 `020` 运行在 tick 4166 直接观测到该生命周期。详见 `docs/determinism-reanimation.md`。

**要点**：这里分歧的不是"画面"，是"什么时候砸下去"。

### 1.4 反面：走路运动学确实与动画解耦

僵尸位移由 `mVelX` 驱动，`mFrame`/`mAnimCounter` 只决定画哪一帧：

```
Zombie.cpp:4847-4921  Zombie::UpdateAnimCounter:
    mAnimCounter++;
    if (mAnimCounter >= mAnimFrames * mAnimTicksPerFrame) mAnimCounter = 0;
    mFrame = mAnimCounter / mAnimTicksPerFrame;
```

`Zombie::UpdateZombiePolevaulter` 行 1734-1737 里那句 `mPosX -= 150.0f * mAnimTime` 紧跟 `mPosX = aOldPosX` 复原，实际是死代码。**[D]**

所以：**"僵尸走得对不对"不依赖动画；"僵尸什么时候动手"依赖动画。**

## 2. 证据 B：动画创建消耗共享 RNG

```
Zombie.cpp:962-983   Zombie::LoadReanim (RVA 0x524470)
    ... Rand(4) ... RandRangeFloat(12,24) 或 RandRangeFloat(12,18) ...
    aBodyReanim->mAnimTime = RandRangeFloat(0.0f, 0.99f);
Zombie.cpp:2598      bobsled follower: mAnimTime = RandRangeFloat(0.0f, 1.0f)
Zombie.cpp:3130-3151 Zombiquarium: Rand(7)，并把 RandRangeFloat(15,20) 写进 mAnimRate
Plant.cpp:530        sleep reanim: mAnimTime = RandRangeFloat(0.0f, 0.9f)
```

**[D]** 全部走全局 MT。含义：**动画对象的创建次数与顺序本身进入随机流**。多一个或少一个动画对象（哪怕只是表现层的），后面的出怪类型、行路、粒子种子全部平移。

同类耦合在粒子侧更严重：`srand(age * particle_address)` 用堆地址做种子，直接污染游戏线程 CRT 流——**[V]**，`0x516b3c`/`0x516ba5` 原字节已核实，见 `docs/particle-shake-determinism.md`。

**这就是"动画差一点没关系"不成立的根本原因**：表现层的差异有一条通道回到模拟。

## 3. 证据 C：动画时间是浮点累加，误差会漂移

`mAnimTime += 0.01f * mAnimRate / mFrameCount` 每 tick 执行一次，一局 55,800 tick 就是五万多次累加。同样输入下，24 位与 53 位精度的结果会在末位分叉，并随时间单调放大。

**[V]** 048 实测的冷启动差异字段正是这一族：x87 控制字 `0x007f`(24 位) 对 `0x027f`(53 位)、雾偏移 `board/0x5d0`、僵尸 `Zombie+0x124`（`mOriginalAnimRate`）、两株植物的 `anim_time_bits`/`last_frame_time_bits`。

由此得到一个反直觉结论：**动画时间不是"比较松"的那部分状态，而是全状态里最容易分叉的那部分**。反过来，只要 FP 环境钉死（`fixed_owner_fp_v1`），它又是最灵敏的分叉探测器——5000 tick 全等的判据里就包含这些字段。**[V]** 见 `docs/fixed-owner-fp.md`。

## 6. 可降级 / 必须保留清单

**可降级为"仅诊断、不参与相等判定"（合计约 13%）**

- `reanimations.nodes[*].state.overlay_matrix_bits`——由位置与缩放派生
- `reanimations.nodes[*].state.extra_additive_color`、`state.track_scalars`
- 僵尸 `mFrame`/`mPrevFrame`、植物 `mFrame`——由 `mAnimCounter` 派生
- 纯计时器：僵尸 `mGroanCounter`、`mJustGotShotCounter`；植物 `mBlinkCountdown`、`mEatenFlashCountdown`

**不能降级，即使只要求"阵型级可重复"**

- `anim_time_bits` / `anim_rate_bits` / `frame_count` / `loop_type` / `loop_count`——玩法事件时钟（§1）
- RNG 两个实例的完整状态——动画与粒子的创建都在消耗它（§2）
- 僵尸位置、`mZombiePhase`、`mPhaseCounter`、血量与护具、`mHasHead`/`mHasObject`；植物 `mPlantHealth`、`mLaunchCounter`、`mStateCountdown`
- 波表、出怪阈值/倒计时、卡片冷却、金币与阳光

## 7. 与"接管式重放器"的关系

把 §1-§3 合起来看，"接管时直接覆盖状态再继续跑"这条路上的一个具体结论是：

- **覆盖必须覆盖动画时钟，不能只覆盖阵型。** 因为下一 tick 的锤击/跳越/吞食判定读的就是它；如果只把植物和僵尸摆回原位而动画进度是新的，第一次砸击的时机就会不同。
- **覆盖还必须是"从 B(0) 起算"的同一进度。** 动画是累加量，把它设成"差不多的值"仍然会在后面的阈值处错开一帧。
- **如果想让覆盖变得便宜，正确做法是改耦合而不是删字段**：把 `Rand`/`RandRangeFloat` 的表现层消费者改到独立随机流，把 `ShouldTriggerTimedEvent(阈值)` 改成按 tick 计数的事件表。改完之后，"动画差一点"才真的无害——但这时它已经不是原版引擎，必须标注 `original_engine_bitwise_unmodified=false`，并且要重新做一轮验收。
