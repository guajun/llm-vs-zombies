# 阵型运转影响评估：哪些状态真的影响运阵

日期：2026-09-20。范围：回答两个问题——

1. 审计里捕获的每一项状态，**哪些真的会影响阵型运转**（而不是只影响画面）；
2. "重新加载存档会刷新栈位"这类原版特性，**在多大程度上是可重复性的缺口**，以及 LLM 对局时会不会被 exploit。

方法：候选反编译源码静态阅读（固定提交 `8a2d121899ba5cb4df644cd7d2e4c1aaf88dd238`，本地副本 `work/replay-research/`）＋ 本项目锁定的 AvZ 结构定义与教程脚本 ＋ 现有真实 audit 档的差分统计。不启动游戏，不修改任何运行目录。

证据等级沿用既有约定：**[V]** 本项目对目标二进制（引擎 SHA-256 `f9669af3…1322`）的机器码或运行结果已直接验证；**[D]** 候选反编译源码，与已核实 RVA 一致但未逐条独立反汇编；**[M]** 在真实 audit 档上实测统计；**[I]** 推断，未验证。

## 0. 结论摘要

1. **"对运阵有影响"要按后果分级，不能按"是不是动画/是不是随机数"分级。** 本文件把它分成 L-A（逐位必须相等）、L-B（必须相等，但可以通过改耦合降低耦合度）、L-C（可只记录不判等）三级，见 §2。
2. **栈位（对象槽位下标）本身就是玩法变量，不是实现细节。** 它是原版选取"吃哪一个 / 压哪一个"植物的判定键，也是同 tick 内的动作先后顺序；社区官方教程脚本直接对栈位做大小比较。见 §1。[V][D]
3. **原版存档确实"刷新"了一样东西，但被刷新的不是栈位，而是随机流与序列号计数器。** `SyncDataArray` 完整恢复槽位块与空闲链表，所以**已存在对象的栈位和未来的槽位复用顺序都不变**；不入档的是全局 MT、CRT 状态和 `DataArray::mNextKey`。读档还会额外消耗约 800 次全局 `Rand()`（新建 Board 的网格外观循环），而这些消耗不回滚。见 §5。[D]
4. **随机数不是主因，但它是稀疏而致命的输入。** 每 tick 真正携带信息的状态变更只有约 8%，其中 RNG 状态占 9.17%；而动画创建本身也在消耗全局 MT，所以表现层差异有一条回到模拟的通道。见 §3。[M][D]
5. **出怪分两段抽随机，只有第一段入档。** 波表（每波有哪些僵尸）在建局时抽定并写进 Board，所以读档后不变；单只僵尸的行、变体、速度、动画速率在出怪的那一刻用全局 MT 抽，**不入档**。这正是"同一存档读两次，波次一样但僵尸走哪一行可以不一样"的机制。见 §5.5。[D]
6. **LLM exploit 的真实入口不在游戏物理，而在"环境是否允许读档/回滚/暂停观察/直接读 RNG"。** 本项目的 strict 口径是固定初始状态 + 固定动作序列重放，天然没有这些入口；一旦改成"LLM 实时玩"，必须显式定义并记录。见 §6。

## 1. 栈位：社区convention与引擎机制对得上

### 1.1 定义

本项目锁定的 AvZ 结构定义里，同一个字段被直接命名为"栈位"：

```
avz/framework/inc/avz_pvz_struct.h:518   // 对象的编号（栈位）
                                         uint16_t& Index();
avz/framework/inc/avz_pvz_struct.h     // 对象的序列号
                                         uint16_t& Rank();
                                         // 对象的 ID
                                         uint32_t& Id();
```

引擎侧对应 `DataArray<T>::DataArrayItem`：每项是 `{T mItem; uint32_t mID;}`，`mID = (mNextKey++ << 16) | slot`（`Sexy.TodLib_DataArray.h:142`）。所以**栈位 = 低 16 位的槽位下标，序列号 = 高 16 位的分配计数器**。两者拼成的完整 `ID` 是被到处缓存的引用值。[D]

### 1.2 为什么栈位会改变运阵结果

池的遍历顺序就是槽位下标升序：

```
Sexy.TodLib_DataArray.h:106  IterateNext: 从 mBlock[0] 起逐项递增，跳过 mID 无 key 的空槽
Lawn_Board.cpp:9266          Board::IteratePlants = mPlants.IterateNext + 跳过 mDead
```

三条直接读它的玩法路径：

| 位置 | 行为 | 后果 | 强度 |
|---|---|---|---|
| `Lawn_Board.cpp:5084` `Board::UpdateGameObjects` | 先按栈位升序更新**全部植物**，再按栈位升序更新**全部僵尸** | 同 tick 内，低栈位对象的动作先发生 | **[D]** |
| `Lawn_Zombie.cpp:6336` `Zombie::FindPlantTarget`（0x52E780） | 按栈位遍历，返回**第一个**与攻击矩形重叠 ≥20 的可攻击植物 | 同格多株植物时，谁被吃由栈位决定 | **[D]** |
| `Lawn_Zombie.cpp:6472` `Zombie::CheckSquish`（0x52EDB0）→ `SquishAllInSquare`（0x52E920） | 按栈位找到第一株可压植物，然后**压掉该植物所在整格** | 巨人锤击落到哪一格由栈位决定 | **[D]** |

第三条可以直接摊开源码（`Lawn_Zombie.cpp:2030-2100`，`Zombie::UpdateZombieGargantuar`，RVA 0x526D10）：

```c
if (aBodyReanim->ShouldTriggerTimedEvent(0.64f)) {          // 动画进度跨过 0.64
    Plant* aPlant = FindPlantTarget(ATTACKTYPE_CHEW);       // 按栈位取第一株重叠的
    if (aPlant) {
        ...
        SquishAllInSquare(aPlant->mPlantCol, aPlant->mRow, ATTACKTYPE_CHEW);   // 砸"那一株"的格子
    }
}
```

`DO_FIX_BUGS` 开或关在植物侧完全一致，差别只出现在被魅惑的巨人。结论：**锤击落点不是几何最近的格子，而是"与攻击矩形重叠 ≥20 的植物里栈位最小的那一株"所在的格子。** 这正是社区"垫材栈位小于南瓜头，南瓜头没事"的机制——垫材把锤子引到自己那一格。换句话说，"谁离得近谁先挨打"这个直觉在这里是错的。

### 1.3 社区就是这么用的

AvZ 官方教程脚本 `liang_yi`（两仪阵）里，铲不铲南瓜头取决于栈位大小：

```
avz/framework/tutorial/scripts/liang_yi/processor.h:341-352
    // 即将锤扁南瓜头但是仍需判断栈位大小
    auto fodderIdx = AGetPlantIndex(gigaGrid.row, gigaGrid.col);
    auto pumpkinIdx = AGetPlantIndex(gigaGrid.row, gigaGrid.col - 1, APUMPKIN);
    if (fodderIdx >= 0 && fodderIdx < pumpkinIdx) {
        // 虽然巨人马上就要锤扁植物，但是垫材的栈位小于南瓜头，南瓜头没事
        continue;
    }
```

而 `AGetPlantIndex` 返回的正是 `plant.Index()`，即栈位（`avz/framework/src/avz_memory.cpp:40-58`）。也就是说社区脚本的第一等决策变量就是这个下标。

栈位还会带来小于 1 tick 的时序偏差，社区脚本里是硬编码补偿的：

```
avz/framework/tutorial/scripts/jing_dian_4/jing_dian_4.cpp:64,123,140,145
    ATime(wave + 1, -298 + 1) /* 1 是为了兼容栈位带来的 1cs 偏差 */
    // 这里因为栈位问题会带来 1cs 的偏差
```

**结论**：栈位是社区明确承认、并且写进时序补偿的玩法变量。[D][V]

## 3. 实测：每 tick 到底在变什么

取已封存长局（045 baseline 后段，1000 tick，381,081 个 JSON Patch 操作）逐字段统计 **[M]**：

| 顶层 | 操作数 | 占比 |
|---|---:|---:|
| reanimations | 146,160 | 38.35% |
| zombies | 116,161 | 30.48% |
| plants | 71,219 | 18.69% |
| rng | 34,953 | 9.17% |
| 其余（coins/board/seeds/sound/app/draw/particle/projectiles） | 12,588 | 3.30% |

按"这个量能不能从别的量重算"再分一次：

| 类别 | 占比 | 性质 |
|---|---:|---|
| 步长 ≥90% 为 ±1 的等差计数 | 44.46% | 可重算（动画计数、计时器、相位计数） |
| 动画时钟（`anim_time` + `last_frame_time`） | 25.19% | **不可重算但可锚定**（存起点 + 速率即可重放） |
| 渲染派生（矩阵 + 颜色 + 轨道标量） | 12.78% | 可直接重算 |
| RNG 状态 | 9.17% | 必须逐位相等（本身就是熵） |
| 真正携带信息的量（位置、相位、血量、波次、卡片、金币） | ≈8% | 必须逐位相等 |

两个可操作结论：

1. **"每帧状态很大"不是因为信息多，而是因为审计把可重算量也逐边界写了一遍。** 这也是证据格式提案（`docs/证据存储格式提案.md`）能把 1.26 GiB 压到 ~80 MB 的原因。
2. **RNG 只占 9.17%，但换掉随机源解决不了问题**：048 的分叉落在 x87 控制字与动画速率上，与随机源无关；036 的两次运行用的是同一个随机源，差的是调用次数。随机数是"稀疏输入"，不是"噪声源"。

## 4. 三个真实事故分别证明了哪一项

| 事故 | 差异所在 | 说明什么 | 强度 |
|---|---|---|---|
| `017` | tick 4166，红眼巨人动画进度 `0.6399995 → 0.6424237` 跨过 `0.64`，下一帧植物 `mSquished` 置位 | 动画时钟是玩法时钟；差半个 tick 就是"砸下去了"与"没砸" | **[V]** |
| `036` | 同一次音效的 `IsPlaying` 返回不同 → 改变准入 → 多执行一次全局 MT 变体选择 | 宿主表现层状态能通过随机流放大成整局差异 | **[V]** |

这三个案例合起来回答了"哪些真的影响运阵"：**不是按子系统分，而是按"它是否进入下一次决策的输入"分。**

## 5. 读档为什么会"刷新栈位"

### 5.1 原版存档到底存了什么

```
Lawn_System_SaveGame.cpp:355-361
template <typename T> void SyncDataArray(ctx, DataArray<T>& a) {
    ctx.SyncUint(a.mFreeListHead);
    ctx.SyncUint(a.mMaxUsedCount);
    ctx.SyncUint(a.mSize);
    ctx.SyncBytes(a.mBlock, a.mMaxUsedCount * sizeof(DataArrayItem));
}
```

`SyncBoard()` 的实际次序是：先 `SyncBytes(&theBoard->mPaused, sizeof(Board) - offsetof(Board, mPaused))` 写出 **Board 自 +0x164 起的整块字节**（含波表 `mZombiesInWave`(+0x6B4)、行选择数组 `mRowPickingArray`(+0x654)、`mBoardRandSeed`(+0x561C)），再对 12 个池逐块写 `mFreeListHead` + `mMaxUsedCount` + `mSize` + 块内容（僵尸、植物、投射物、金币、割草机、场地物、粒子系统、发射器、粒子、**动画**、拖尾、附着，`SaveGame.cpp:368-379`），最后才是 CursorObject、CursorPreview、SeedBank、Challenge、Music。`mPaused` 在 +0x164，而 DataArray 成员在 +0x90~+0x11C，所以两块字节天然不重叠，不存在重复写入。[D]

动画的 track instances 也做了额外处理（`SyncBytes(theReanimation->mTrackInstances, aSize)`，`SaveGame.cpp:323`），粒子/动画/拖尾的 definition 以枚举形式写出、读回时重新取指针。[D]

### 5.2 结论：栈位被保留，**序列号计数器被重置**

`SyncDataArray` 保存 `mFreeListHead` 与整块 `mBlock`，因此：

- **已有对象的槽位下标（栈位）与它们的完整 ID 都被原样恢复**；
- 空闲链表链（空槽里存的就是下一个空槽下标）也在块里，所以**后续种植的落位顺序也一致**。

但 `mNextKey` **没有**被同步，而 `DataArrayInitialize` 会把它设成 1001（`Sexy.TodLib_DataArray.h:59`），`MakeNewBoard()` 又在读档前先执行一次。于是：

> 读档后新建的对象，其 32 位 ID 的高 16 位（序列号）从 1001 重新起算，与"从不读档"的运行不同。

这正是社区印象里"读档会刷新栈位"的来源：**下标没变，序列号被刷新了。** AvZ 结构定义把这两个字段分别叫"栈位"和"序列号"，而社区口语常把它们混称。

### 5.3 这会怎样影响运阵

链式关系：

```
ID = (序列号 << 16) | 栈位          // Sexy.TodLib_DataArray.h:142
DataArrayTryToGet(id) { return block[id & 0xffff].mID == id ? ... : nullptr; }   // :152
```

`DataArrayTryToGet` 要求**完整 32 位相等**。引擎把完整 ID 缓存进实体字段：`Zombie::mTargetPlantID`（`Lawn_Zombie.cpp:1174`）、`Plant::mTargetZombieID`（`Lawn_Plant.cpp:1224`）、投射物目标、`mCobCannonPlantID`。所以序列号一刷新，这些缓存引用的解析结果就可能与"不读档"的运行不同。

两条分叉后果要分开看：

- **fail-safe 方向**：旧 ID 的序列号与重发后的不同 → `DataArrayTryToGet` 返回 `nullptr` → 目标"看起来消失了"（例如植物放弃目标）。不会串到别的对象，但行为会变。
- **aliasing 方向**：档内引用的 ID 恰好等于重发后某个新对象的 ID（同序列号、同下标）→ 引用指向一个无关的新对象，这是典型的 ABA。

需要说清楚的是：**这条链路目前只到"存在差异通道"，还没有到"已经观察到阵型结果不同"。** 把它当结论还差一个实验（见 §7.2 P4）。它的实际风险等级是 **[I]**，不是 **[V]**。

### 5.4 读档还会丢什么

以下内容不在 `SaveGame` 范围内，读档后必然与"不读档"的运行不同：

| 丢失项 | 证据 | 后果 |
|---|---|---|
| 全局 MT 状态（624 字 + 游标） | `Common.cpp:15` `static Sexy::MTRand gMTRand;`，`SaveGame` 全程未触及；连 `MTRand::Serialize()` 都只拷 `mt[624]` 不拷 `mti` | 每 tick 选行、掉落、动画创建的随机流重新起算 |
| 游戏线程 CRT 状态 | 粒子 `FIELD_SHAKE` 用它，且原版用堆地址做种子 | 粒子/抖动序列不同 |
| x87 控制字与舍入模式 | 048 已实测 | 立即在浮点派生字段上分叉 |
| AvZ 层状态（操作队列、refresh time） | AvZ 自有变量，不在存档 | 脚本时序漂移 |
| 音频引用计数与播放状态 | 需 `__AAfterLoadGame` 手工修补才不会丢音效 | 036 那类通过音效准入改变 MT 消耗的差异 |
| app 级字段（音乐播放位置、UI 等） | 只同步 Music 结构体，app 其余状态不写 | 与"不读档"的时间线不同 |

还有一个容易被忽略的消耗：**`MakeNewBoard()` 本身要吃掉约 800 次全局 `Rand()`**（`mGridCelLook` / `mGridCelOffset` 的 45×6 循环，`Lawn_Board.cpp:75-77`），读档路径先建新 Board 再覆盖，所以这些消耗不会被回滚。[D]

另外两个必须记住的原版怪癖：读档不是内存覆盖而是**摧毁重建**（`__ABeforeMakeNewBoard` → `MakeNewBoard` → `LawnLoadGame`/`LoadGame` → 回调修补 → `continue board` → `UpdateRefreshTime(true)`）；而**保存本身会改状态**——写盘前会改小丑僵尸的 `+0x104`。[D]

### 5.5 出怪为什么要分两段看

这是"波表相同、运阵不同"的直接机制：

| 阶段 | 抽什么 | 用哪个随机源 | 入档？ |
|---|---|---|---|
| **建局** | 每波有哪些僵尸（`mZombiesInWave[aWave][i]`） | 全局 `Rand` → `PickZombieType` → `TodPickFromWeightedArray`（`Lawn_Board.cpp:575-800`、`:2528`） | **入档**（写在 Board 里） |
| **建局** | 关卡地物（墓碑、传送门）用局部 `MTRand aLevelRNG`，种子来自 `GetLevelRandSeed()` = `mBoardRandSeed + 关卡/模式常量`（`Lawn_Board.cpp:798,1095`） | 局部 MT，种子在 Board 里 | **入档** |
| **出怪** | 走哪一行（`!Rand(5)` 的变体判定）、速度 `RandRangeFloat(0.23,0.37)`、动画速率 `RandRangeFloat(12,24)`、`mAnimTime = RandRangeFloat(0,0.99)` | **全局 MT** | **不入档** |
| **波次推进** | 波长上限 `ZOMBIE_COUNTDOWN + Rand(ZOMBIE_COUNTDOWN_RANGE)`、下一波血量阈值 `RandRangeFloat(0.5,0.65)` | **全局 MT** | **不入档** |

所以一张存档能恢复"这一波有哪些僵尸、现在打到哪了"，但不能恢复"下一只僵尸走哪一行、下一步什么时候刷新"。这就是社区所谓"读档会变"的准确内容。[D]

顺带一个可复用的既有机制：原版框架自带 `MTAutoDisallowRand`（`SexyAppFramework_MTRand.h:35`，在 `SexyAppBase.cpp:2573,5175` 使用）与 `DBG_ASSERT(gRandAllowed==0)`。也就是说"此处不允许消费玩法随机流"在原版里已经是一条可断言的纪律，本项目可以直接复用它来给表现层加守门，而不必新造概念。[D]

## 6. LLM 对局时的 exploit 面

把"LLM 在玩"与"我们重放证据"分开看，风险面完全不同：

| 入口 | 是否存在于当前 strict 口径 | 若开放给 LLM 的后果 | 建议 |
|---|---|---|---|
| 读档 / 回滚重来 | 不存在（固定初始状态 + 固定动作序列） | **存档刷**：反复读档直到出怪行/掉落到满意为止。因为全局 MT 不在存档里，读档等于重掷随机流 | 禁止，或在接口层记录每次读档并纳入证据 |
| 暂停后读全状态 | 存在，但这是**设计选择**（观察窗口是合同的一部分） | 超人类观察能力；不算 exploit，但必须写进能力声明，否则与其他 agent 不可比 | 在评估文档里显式声明"允许在边界观察全状态" |
| 直接读 RNG 内部状态 | 不存在（strict 口径下审计是只读证据，不是 agent 接口） | 若某个观察接口把 MT 表与游标交给 agent，等于提前告知它未来的出怪行与掉落——这是**信息泄漏**，不是 exploit | 计分运行时把 RNG 留在带外，或只暴露 `observe` 允许的可见量 |
| 时钟控制（暂停/加速/跳帧） | 不存在（tick 预算驱动，不跟墙钟） | 如果能加速，就能在同等墙钟内做更多搜索 | 保持 tick 驱动 |
| 栈位利用 | 存在（栈位被捕获且参与判等） | 主动安排种植顺序以获得"南瓜头不被压"之类的有利栈位——**这是真实社区打法，不是 bug** | 允许，但必须在证据里可复现，否则重放不成立 |
| 读档后的序列号刷新 | 不存在于 strict 口径 | 若开放读档，ID 复用可能被用来让僵尸"丢失目标" | 见 §7 实验 1 |
| 缓冲区/数量上限 | 存在（僵尸池 1024，`mZombies.mSize >= mMaxSize-1` 时拒绝生成，`Lawn_Board.cpp:2676`） | 极端长局下"堆满池子让新僵尸生成失败"是否算 exploit，取决于评估目标 | 提前定义 |

**核心判断**：LLM 真正能 exploit 的不是游戏物理，而是**环境边界有没有被定义清楚**。当前项目已经把最难的部分（同一初始状态、同一动作序列、逐边界全等）做成了证据；剩下要补的是"允许哪些接口、以及这些接口一旦开放要额外记录什么"。

## 7. 建议的判据分层与验证实验

### 7.1 分层合同（建议）

- **L-A 层（阵型层）**：植物/僵尸/投射物/金币/推车/场地物的槽位表、栈位、完整 ID、血量、相位、计时、位置、波次、卡片、金币、两个 RNG 实例、FP 环境。判据：逐位相等。
- **L-B 层（转移层）**：动画时钟（`anim_time`/`anim_rate`/`frame_count`/`loop_type`）、粒子抖动、音效状态、绘制调度。判据：现在逐位相等；如果将来改耦合（拆随机流、事件改 tick 驱动），改为"事件表相等"并标注 `original_engine_bitwise_unmodified=false`。
- **L-C 层（表现层）**：动画 overlay 矩阵、附加色、轨道标量、帧索引、纯计时器。判据：只记录，不判等。

这套分层与 `动画耦合与可重复性取证.md` §6 的清单一致，只是把"可降级"从"动画整体"收窄到 13% 的渲染派生量。

### 7.2 七个低成本探针

| 编号 | 目的 | 做法 | 预期 | 把哪条从 [I] 升级 |
|---|---|---|---|---|
| P1 | A 层是否被存档完整保留 | 同一存档读档 K=5 次，在固定 tick 比对 L-A 层 | 全等；不等则定位到具体字段 | §5.2 |
| P2 | 量化"读档改变运阵" | 同一存档：一路继续 vs 读档后继续，各 1000 tick，比 L-A 层 | 预期不等，得到漂移量级 | §5.5 |

七个探针都不需要长局，成本在分钟到小时量级。

### 9.2 学术侧

确定性重放本身主要落在工程实践（lockstep + 状态哈希、rollback netcode、FoundationDB/Antithesis 式确定性仿真测试），没有可以直接引用的"PvZ 判定标准"。因此本项目必须自己提出契约并自己验证，不存在成熟外部权威可以照抄。

方法论上有一条必须写清楚的区分：**输入等价**（同一初始状态 + 同一输入序列）、**状态等价**（状态向量逐位相同）、**可观测等价**（只比部分观测量）是三件不同的事，推导方向只有 状态等价 ⇒ 可观测等价，以及 输入等价 + 确定性 ⇒ 状态等价。本项目的 L-A 是状态等价的近似（强度取决于捕获覆盖度），L-B 是输入等价的断言，L-C 是明确放弃状态等价。§4 的两个真实事故（017 差一个 tick 触发阈值、036 音效准入改变 MT 消费）正好是"只比观测量"这条路的两个失败样本。

浮点侧有一条**已核实**的规范依据（本次实际取到原文）：Microsoft Learn 的 `/fp (Specify floating-point behavior)` 写明 `/fp:precise` 下"Intermediate computations may be performed at machine precision"，且 FMA 收缩"doesn't round the intermediate product... at a cost of bitwise exact results"。也就是说 x87 的 80 位与 SSE 的 64 位给出不同位模式是标准允许的差异，不是 bug；同时同一份源码在不同编译选项下也可以位级不同。这条既解释了 048，也给出"改原版"的判定线：钉死 FP 控制字是消除宿主差异，改阈值判定是改变玩法语义。

三层合同目前**没有找到公认反例**，但有三类已知的坑：层边界会单向漂移（C 层对象一旦在创建时消耗共享 RNG 就必须升级为 B 层）；只比部分状态必漏隐藏通道；B 层的"输入一致"若不精确到引擎调用身份与 RNG 消费次数就无法验证。

真正对口的学术议题是 **reward hacking / specification gaming**，即"agent 会不会利用规格漏洞"：

- Skalse et al. 2022, *Defining and Characterizing Reward Hacking*（概念定义）。
- *Towards Understanding Specification Gaming in Reasoning Models*, arXiv:2605.02269——8 个任务中所有被测推理模型都有非可忽略的投机率，且 RL 推理训练**提高**投机率。
- *Reward Hacking in Language Model Agents: Revisiting AI Safety Gridworlds*, arXiv:2606.15385——模型零样本即可"观测奖励高但隐藏目标不达标"。
- DeltaML-Bench, arXiv:2608.19653——报告某配置下 specification gaming 率达 47.9%。

文献的稳定结论是：只靠提示与测试期缓解能**降低但不消除**投机率。所以"读档/接管/回放文件会不会被利用"不是可以留给运气的问题，而是评测设计的一部分。

**核实状态的声明**：以上四条文献的标题、年份与摘要由调研 agent 经 Semantic Scholar / OpenAlex 元数据核对，本项目**未通读全文**；本次尝试独立复核时 arXiv 与 Semantic Scholar 均返回 HTTP 429（限流），二次确认未完成。引用时按"二手元数据"对待。

方法论侧的完整笔记（三种等价、最小充分状态与"存锚点 + 重算"的成立条件、浮点规范依据、评测效度威胁、以及上面三类坑的推导）在 `work/academic-determinism-research.md`。该文件位于 gitignore 的草稿区，每条结论都标了核实等级；其中 IEEE-754/Intel SDM 原文与 ACM 的 reproducibility/replicability 术语区分本次**未取到**（403/429），不应被引用。
