# 并行实验约定：独立检出 + 最后联合实验结果

日期：2026-09-23。对应 issue [#57](https://github.com/guajun/llm-vs-zombies/issues/57)，来自 [#50](https://github.com/guajun/llm-vs-zombies/issues/50) / [#51](https://github.com/guajun/llm-vs-zombies/issues/51) 两条线的真实运行。

范围声明：本文是**开发约定**，不改 runner 代码、不加锁、不改任何既有结论。它只规定"多个平行世界同时跑"时检出、构建与联合报告的目录与校验要求；不放宽任何实验门槛，也不把已失败的原档改写成通过。

## 1. 背景与证据

## 2. 约定

### 2.1 每个平行世界一份独立检出、一份独立 build 目录

| 要求 | 做法 | 现有机制依据 |
|---|---|---|
| 每世界一份检出 | `git clone --depth 1 file:///F:/llm-vs-zombies work/lvz-w1`（或 `git worktree add`，但 `worktree` 共享 `.git`，同样必须自带 `build/`） | 根仓库工作树只读：`.gitignore:4-6` 已忽略 `build/`、`work/`、`third_party/`，检出内这些目录互不影响 |
| 每检出自带 build 目录 | 不做任何路径覆盖：构建目录固定为 `<检出>/build/cmake` | `tools/build-avz.ps1:8`；`src/llm_vs_zombies/evaluation.py:218-221`（`root/tools/build-avz.ps1`、`launcher/build.ps1`、`ctest --test-dir build/cmake`，工作目录为 `root`，见 `evaluation.py:229`） |
| run 的 root 跟随检出 | `python -m llm_vs_zombies.evaluation run` 不传 `--root` 时，root 取"运行该模块的检出" | `src/llm_vs_zombies/evaluation.py:982`（`default=Path(__file__).resolve().parents[2]`）；即"用哪个检出的 `PYTHONPATH=src` 起跑，产物就落在哪个检出" |
| 命名带世界前缀 | 计划文件 `work/<world>-plan.json`，run 目录 `experiments/runs/<world>-*`（沿用 `m1-par-c` / `m1-par-d` 的写法） | `src/llm_vs_zombies/cli.py:21-26`（run 名只允许字母/数字/`-`/`_`） |
| **禁止同一检出并发起多个 run** | 同一检出的 run 必须串行——包括 `--skip-build`：它跳过构建，但仍会在同一检出里写 `experiments/runs/`、`work/`、`build/recorder.cfg` 与沙箱 | `cli.py:105` 写 `<root>/build/recorder.cfg`；`cli.py:23-26` 建 run 目录；`evaluation.py:222-225` 往 run 目录写 `build-and-tests.log` |
| 根仓库不做并行宿主 | 根仓库 `F:\llm-vs-zombies` 只作为克隆源与本地游戏文件来源，不再承载任何世界的 run | 本文；`game/original/`、`game/local-engine/` 仍在 `.gitignore:7-8` 内，属本机私有依赖 |

|---|---|---|

### 2.3 为什么不采用加锁方案

| 理由 | 说明 | 依据 |
|---|---|---|
| 锁只覆盖构建步，冲突面远不止构建 | 同一检出里还有 `experiments/runs/<name>`、`work/*.json`、`build/recorder.cfg`、`avz/runtime`、`game/local-engine` 等共享写点 | `cli.py:23-26,105`；`tools/bootstrap.ps1:9-12` |
| 锁把"并行"改成"排队"，目标丢失 | 约定要的是多个世界**同时**产出各自证据；排队既没有并行收益，也没有隔离 | 本文 §1 |
| 锁掩盖问题 | C 档的正确结论是"这次运行无效，不能当代码/游戏结论用"，而不是"再等一会儿就会好"；只有独立检出能让失败定位到单一世界的目录 | §1.1、§1.3 |
| 缺少可用的锁设施 | 现有 harness 只有 worker 自有的 Windows Job 与设备租约，都是**分支内**隔离，没有检出级的跨进程互斥；加锁要新增锁文件、超时、残留清理与其自身失败模式 | `docs/并行分支worker.md:54-88`；[待核实]：锁方案的开销与失败模式未实测 |
| 成本对比 | `--depth 1` 本地克隆是一次性成本，且带出自带工具链后各世界的构建产物可独立复用 | [待核实]：克隆与首次 bootstrap 的耗时未实测 |

结论：不采用加锁方案。并行世界用**独立检出 + 自带工具链 + 联合校验**隔离，而不是把共享检出串行化。

### 2.4 与既有两条并行管线的边界

| 管线 | 并行对象 | 隔离粒度 | 失败策略 | 文档 |
|---|---|---|---|---|
| 并行冷重放（#19） | 同一条源轨迹的冷重放 | 每次 cold 一个宿主进程、独立 run 目录与独立 Job；父进程串行预热 FNV 缓存并锁定源码 SHA256 | 首败停派 | `docs/parallel-cold.md:19-38` |
| 并行分支 worker（N10） | 训练管线的同根多分支 | 每分支一份用户档、日志、设备租约，工作区在同一检出内 | 首败不停派 | `docs/并行分支worker.md:54-100` |
| 本文 | **跨检出的平行世界**（各自 root） | 每世界一份检出与 build 目录 | 各世界内按自己的门槛，合并前另加身份校验（§3） | 本文 |

三条管线共用"PID/创建时间绑定 + 自有 Job + 只读回执"的写法，但门槛与失败策略分开定义；本约定不替代前两条的任何结论。

### 2.5 用 `tools/prepare-checkout.ps1` 准备检出（本机实测）

§2.2 的前提是检出里有 **`work/`、AvZ 子模块内容、`avz/runtime`、自带工具链**四样东西，而它们全在 `.gitignore` 里，新克隆一份都没有。2026-09-23 的一次实测里，为了赶时间手工 clone + 手工解压工具链、跳过了脚本，连续踩到下面四个坑。现在这四件事由 `tools/prepare-checkout.ps1` 一次做完，并在**该检出内**做"构建 + ctest"自检，因此也可以只用一条命令准备一个平行世界：

```powershell
# 每个世界一份独立检出；本节用 clone（worktree 的注意事项见 §2.1），各自带 build/ 与 third_party/
git clone --depth 1 https://github.com/guajun/llm-vs-zombies.git work\lvz-w1
cd work\lvz-w1
./tools/prepare-checkout.ps1                  # 补齐 work/、子模块、注入器、工具链 + 自检（构建、launcher、Python 测试、ctest、写一份 plan）
./tools/prepare-checkout.ps1 -VerifyOnly      # 只校验不重建；缺项时给出要跑的那条命令（CI 可用）
./tools/prepare-checkout.ps1 -SkipSelfCheck   # 只补齐，不构建
./tools/prepare-checkout.ps1 -Offline -ToolchainSource ..\..\work -AvzSource ..\..\avz\framework
                                              # 全程不联网：工具链 zip 与 AvZ 子模块都取本地副本
```

| # | 手工准备会踩到的坑 | 脚本现在怎么做 |
|---|---|---|
| 1 | `evaluation plan` 写不出 plan（`FileNotFoundError: work\<name>.json`） | 建 `<检出>/work/`，并用 `evaluation plan` 真的写一份 `work/prepare-checkout-plan.json` 当自检 |
| 2 | `build_and_tests: fail`，CMake 配置失败（`avz/framework/inc` 不存在） | `git submodule update --init --depth 1 avz/framework`，再核对 `avz/framework` HEAD == `dependencies.lock.json:avz_commit`、工作树干净、`submodule.avz/framework.url` 已登记（否则 `git submodule status` 会显示 `-`） |
| 3 | 曾出现 `runtime/avz_overlay.cmake:17` 的 `Pinned AvZ hook/script source changed`，当时归因未定 | **已定因**，见 §2.5.2：那不是内容变了，而是子模块没检出、三个文件根本不存在；脚本在 build 之前先做 pin 预检，缺文件就直说"文件缺失" |
| 4 | run 启动后被拒：`runtime declares the fixed MJ clock anchor; declare the fixed B(0) target explicitly` | 与准备检出无关，属配方声明问题，见 §2.5.1 |

结论不变（**独立检出**），但**准备方式走 `tools/prepare-checkout.ps1`**：它按顺序做题 1-3，并在末尾自检，所以失败点落在"准备"阶段而不是 CMake 或 run 阶段。`tools/bootstrap.ps1` 保留为兼容入口，等价于 `prepare-checkout.ps1 -SkipSelfCheck`（`tools/ci.ps1` 继续用它）；`prepare-checkout.ps1 -VerifyOnly` 完全不写、不下载、不构建，只读校验 + 一条临时探针文件。

#### 2.5.1 B(0) 归一化目标必须显式声明

第 4 条不是"准备检出"的问题，而是**配方声明**的问题，先在这里留接口约定：

- 形如 `mj_clock`、`app_update_count` 这类**取决于 B(0) 之前 App 实时循环跑了多久**的字段，必须在配方里给出**声明的固定目标值**；缺省回退到"本 run 观测值"只保证世界内一致，跨世界必然不同
- 目标值、理由与回执形状见 `docs/b0-归一化提案.md`（#63）；`app_update_count` 的声明式改造见 #64
- 在声明式配置落地前，plan 里的 `mj_clock` 需要手工填值才能跑通；这属于过渡状态，不是长期做法

#### 2.5.2 第 3 条已定因（2026-09-23）：子模块为空，不是内容变了

`runtime/avz_overlay.cmake` 第 17 行同时承担两种完全不同的失败：**文件缺失**与**内容不符**。机制在本机（cmake 4.3.3）实测如下：

- `file(READ <缺失文件> <变量>)` 只报一条**非致命**错误，把变量留成空串，configure 继续往下跑；
- 空串照样走 `string(REPLACE "\r\n" "\n")` 与 `string(SHA256)`，得到 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`（空串 SHA256；用 `cmake -P` 复现过），自然不等于任何锁定值；
- 于是第 17 行抛出与"内容变了"**一字不差**的 `Pinned AvZ hook/script source changed`。

**反证：内容侧从未对不上**

- `work/world-e`、`work/world-f` 的子模块都停在 `c42676c269b5b482a1eb9203a5b979e9d8a2a5c7`，四个受哈希文件（`avz_script.cpp` / `avz_hook.cpp` / `avz_card.cpp` / `avz_smart.cpp`）的归一化 SHA256 全部等于 `runtime/avz_overlay.cmake` 的锁定值；
- 2026-09-23 本次流程又跑了两个全新检出（`work/p3-world-c`、`work/p3-world-d`）：每个文件的归一化 SHA256、锁定值、字节数、CRLF 对数与孤立 CR 数都写进 `<检出>/work/prepare-checkout-report.json`，四个文件全部 `match: true`，随后各自构建成功、`100% tests passed, 0 tests failed out of 21`。

**结论**

1. 第 3 条**不是**换行/`core.autocrlf` 问题（PR #73 撤回的说法继续维持撤回），也**不是** pin 写错；它是"子模块为空 ⇒ 变量为空 ⇒ 空串杂凑不等于 pin"的误报。
2. 下次看到 `Pinned AvZ hook/script source changed`，先在同一份日志里找 `:5/:6/:7` 的 file-open 错误：有 ⇒ 文件缺失（跑子模块步骤）；没有 ⇒ 才是真的内容差异。
3. 工具侧教训：这份哈希必须**完全复刻 overlay 的三步**（`file(READ)` → `string(REPLACE "\r\n" "\n")` → `string(SHA256)`）。手写"归一化 SHA256"很容易算错，本次实现就先犯过一次——把 `\r\n` 整对删掉而没补回 `\n`，10516 B 的源算成 10191 B，于是误报"内容变了"。`tools/prepare-checkout.ps1` 因此直接让 CMake 自己算（生成临时 `-P` 脚本跑同样三步），PowerShell 实现只作为没有 cmake 时的回退。

## 3. 最后联合实验结果

### 3.1 收集

1. 每个世界在自己的检出里跑完 run（源 `-s42-c0`、冷重放 `-s42-c1`、恢复 `-s42-recovery` 都属于该世界）。
2. run 目录**只读复制**到一份联合报告目录，例如 `work/joined-<date>/<world>/`；复制内容至少含 `manifest.json`、`evaluation.json`、`evaluation.md`、`launcher.json`、`initialization-recipe.json`、`evaluation-host-final.json`、`inputs/implementation.zip` 与各 session 目录。
3. 报告按世界分组：世界 → 检出（HEAD + 是否 dirty）→ run 列表 → 每个 run 自己的门槛表（**原样抄录，不重算**）。
4. 失败的世界与失败的 run 一并进报告，不删除、不改写原档（沿用 `docs/parallel-cold.md:27-37` 的"真实失败保留"）。

### 3.3 两个不能直接当身份用的字段（本机实测）

| 字段 | 问题 | 实测 |
|---|---|---|
| `manifest.json.implementation.source_archive_sha256` | 它是对 ZIP **字节**的哈希，而 ZIP 每条记录带 mtime；归档里合成的 `ARCHIVE-REBUILD.md` 条目时间戳随写入时刻变化 | 同一次 D 的两次会话：c0 `f9d0c1c6830b47ac0cffbdf6d62d64d511b148fbf3cfa5a0e994adb2f900d5a5` vs c1 `3190e90386eae1b37b8b86d27f61e14727a2c5a4a76a63854b771804c3d106e5`；但两份归档 272 个条目的 CRC 与大小完全一致，唯一 `date_time` 差异是 `ARCHIVE-REBUILD.md`（02:03:50 vs 02:10:10）→ 源码相同、字节哈希不同 |
| `manifest.json.runtime_hello_sha256` | 它是 runtime hello 的哈希，含 PID / 会话名 / 分支 id | D c0 `76f3381049f935c0a079ae27309af23cf6cef4033059449b600c8f2c3e1e0f09` vs c1 `159a0d0f2aa56050e8c92a332fabaca555e243c11c323146bf5289cd875aabee`；同一次运行的两次会话必然不同 |

替代做法：源码身份用"检出 HEAD + 工作树是否 dirty + `source_files` 逐文件摘要 + ZIP 条目级摘要"；runtime/引擎身份用 `launcher.json.hello.build.avz_commit`、`module_hashes.recorder.dll` 与 `input_hashes`。

### 3.4 与 runner 自带复核的关系

- 每个 attempt 结束时 runner 会复核该 run 目录内门槛声明的产物哈希（`src/llm_vs_zombies/evaluation.py:401-416`），并在会话开始时把当前源码与归档比对，写出 `unchanged` / `matches_archive`（`src/llm_vs_zombies/evaluation_support.py:209-235`）。
- 这些复核只覆盖**单个 run 自洽**；跨世界的可比性目前没有现成工具：§3.2 的校验是手工/脚本步骤，尚未落成 `tools/` 下的命令 —— [待核实]（是否落成校验器由后续 issue 决定）。
- 校验通过只表示"可以进同一份报告做比较"，**不升级任何 run 自己的门槛结论**，也不替代两旗 / 十次冷启动的严格验收（`docs/parallel-cold.md:19-38`）。

## 5. 落地示例

下面是一段可直接照抄的完整流程（Windows / PowerShell；两个世界各自独立检出，最后收集 run 目录并校验身份）。

### 5.1 两个独立检出

```powershell
$root = 'F:\llm-vs-zombies'
$w1 = Join-Path $root 'work\lvz-w1'
$w2 = Join-Path $root 'work\lvz-w2'

# 1) 两个独立检出（本地克隆，depth 1；根仓库不参与并行）
git clone --depth 1 file:///F:/llm-vs-zombies $w1
git clone --depth 1 file:///F:/llm-vs-zombies $w2

# 2) 每个检出自己补齐 work/、AvZ 子模块、注入器与自带工具链，并各自完成"构建 + ctest + 写 plan"自检
foreach ($w in @($w1, $w2)) {
    & (Join-Path $w 'tools\prepare-checkout.ps1')
}
```

`prepare-checkout.ps1` 会自己找到根仓库已下载的 `work\llvm-mingw-20260908.zip` 并校验 SHA256，所以两个世界不会各下载 190 MB；要并行准备就开两个窗口同时跑这两条命令。事后只做校验不重建用 `-VerifyOnly`，完全离线用 `-Offline -ToolchainSource ..\..\work -AvzSource ..\..\avz\framework`，四个开关的完整说明与四个坑的对照表见 §2.5。

### 5.2 各自起 run（两个窗口同时执行；同一检出内不要并发）

```powershell
# —— 世界 1 ——
Set-Location F:\llm-vs-zombies\work\lvz-w1
$env:PYTHONPATH = 'src'
python -m llm_vs_zombies.evaluation plan work\plan.json --tier smoke --seeds 42 --cold-starts 1 `

$env:PYTHONPATH = 'src'
```

### 5.4 合并前校验（源码检出身份 / 引擎与 DLL 哈希 / 初始化配方 / 卡序）

```powershell
function Get-ZipContentDigest([string]$zipPath) {
    Add-Type -AssemblyName System.IO.Compression.FileSystem
    $zip = [System.IO.Compression.ZipFile]::OpenRead($zipPath)
    try   { $lines = $zip.Entries | Sort-Object FullName | ForEach-Object { "$($_.FullName):$($_.Length):$($_.Crc32)" } }
    finally { $zip.Dispose() }
    $sha = [System.Security.Cryptography.SHA256]::Create()
    try { $digest = $sha.ComputeHash([Text.Encoding]::UTF8.GetBytes(($lines -join "`n"))) }
    finally { $sha.Dispose() }
    -join ($digest | ForEach-Object { $_.ToString('x2') })
}

function Get-WorldFingerprint([string]$checkout, [string]$run) {
    $m = Get-Content (Join-Path $run 'manifest.json') -Raw | ConvertFrom-Json
    $l = Get-Content (Join-Path $run 'launcher.json') -Raw | ConvertFrom-Json
    $r = Get-Content (Join-Path $run 'initialization-recipe.json') -Raw | ConvertFrom-Json
    $h = Get-Content (Join-Path $run 'evaluation-host-final.json') -Raw | ConvertFrom-Json
    $sources = ($h.source_files.PSObject.Properties | Sort-Object Name |
                ForEach-Object { "$($_.Name)=$($_.Value)" }) -join '; '
    [ordered]@{
        checkout_head   = (git -C $checkout rev-parse HEAD)
        checkout_dirty  = -not [string]::IsNullOrWhiteSpace((git -C $checkout status --porcelain | Out-String))
        source_files    = $sources
        source_zip      = (Get-ZipContentDigest (Join-Path $run 'inputs/implementation.zip'))
        recorder_dll    = $l.module_hashes.'recorder.dll'
        launcher_exe    = $l.module_hashes.'lvz-launcher.exe'
        bootstrap_dll   = $l.module_hashes.'lvz-bootstrap.dll'
        engine_local    = $l.input_hashes.'game/local-engine/PlantsVsZombies.exe'
        engine_original = $l.input_hashes.'game/original/PlantsVsZombies.exe'
        game_dat        = $l.input_hashes.'game/original/PlantsVsZombies.dat'
        scenario_save   = $l.input_hashes.'experiments/scenarios/liangyi/game1_13.dat'
        avz_commit      = $l.hello.build.avz_commit
        seed            = $r.seed
        clock_anchor    = ($r.clock_anchor | ConvertTo-Json -Compress)
        execution_mode  = $r.execution_mode
        fixed_fp        = "$($r.fixed_fp.mode)/$($r.fixed_fp.mxcsr_control)/$($r.fixed_fp.x87_control)"
        card_order      = (($l.initial_observation.seeds | Sort-Object slot |
                            ForEach-Object { if ($_.type -eq 48) { $_.imitator_type + 49 } else { $_.type } }) -join ',')
    }
}

$worlds = @(
    [pscustomobject]@{ name = 'w1'; checkout = $w1; run = (Join-Path $join 'w1\lvz-w1-s42-001') },
    [pscustomobject]@{ name = 'w2'; checkout = $w2; run = (Join-Path $join 'w2\lvz-w2-s42-001') })
$fps = $worlds | ForEach-Object { [pscustomobject]@{ name = $_.name; fp = (Get-WorldFingerprint $_.checkout $_.run) } }

$report = foreach ($field in $fps[0].fp.Keys) {
    $values = @($fps | ForEach-Object { [string]$_.fp[$field] })
    [pscustomobject]@{
        field   = $field
        values  = ($values -join '  |  ')
        verdict = $(if (($values | Select-Object -Unique).Count -eq 1) { '一致' } else { '不一致' })
    }
}
$report | Format-Table -AutoSize -Wrap
if ($report.verdict -contains '不一致') { throw '检出身份 / 哈希 / 初始化配方不一致：不得合并' }
```

校验通过后把 `$report`、各 run 的门槛表与失败清单写进联合报告；`checkout_dirty = True`、任一哈希或配方不一致、卡序不同，都按 §3.2 记差异并**拒绝合并**。

本机实测：把上面 `$worlds` 的两个 `run` 指向 `experiments/runs/m1-par-d-s42-c0` 与 `experiments/runs/m1-par-d-s42-c1`（同一检出、同一次运行的两个会话），§5.4 代码逐行输出"一致"，其中 `source_zip`（条目级摘要）与 `source_files` 都相等；若改用 §3.3 里那两个字段参与比较，则会出现并非源码差异的假差异。

## 6. 明确不做

1. 不改 runner / launcher / 构建脚本，不引入锁，不新增共享构建目录。
