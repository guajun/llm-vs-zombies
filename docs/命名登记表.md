## 1. 基线与检索方法

- 仓库/基线：`guajun/llm-vs-zombies`，分支 `main`，提交 `dd06f16fc5da34d99204d4a28a913b0b08a7f741`（克隆在 `work/cli-naming`，工作分支 `codex/naming-registry`）。
- 检索范围：232 个仓库内文本文件；排除 `third_party/`、`build/`、`.git/` 与二进制/归档扩展名。
- 三类模式（逐行正则，含 `capabilities.<名>` 形式）：
  - 能力模式名：`[a-z][a-z0-9_]*_v<数字>`
  - schema 名：`lvz.<kebab>[.<段>].v<数字>`
  - 错误码：`Error(<id>,"<code>",…)`、`fail("<code>")`、`ParseSpawnAction.request.error`，以及以变量发出的原因码（`no_game_tick` / `step_count_mismatch`）。
- 来源列：引入该字符串的提交（`git log -S`，在只读根仓库的 `main` 上执行）；`PR #NN` 取提交信息里的编号；issue 号取提交信息或仓库文档（`docs/implementation-board.md`、`docs/分支数据合同与实施计划.md`、文件内注释）的显式引用，早期未标编号的提交按提交信息原样登记。
- 影响面列：全仓引用位置（文件:行），按代码/测试/文档/其他分类；表内给代表值与文件数，全量见 JSON。

补充观察（不另计条目）：
- 能力命名空间实际混装三类东西：方法名（`observe`/`commit`/`pause`…）、特性布尔（`spawn_action`、`branch_rebind`、`prepare_render`）与带版本的模式名（`*_v1`）。
- 同一能力同时给出带版本与非版本键的共有 3 对：`app_update_anchor` / `initial_app_update_anchor_v1`、`mj_clock_anchor` / `initial_mj_clock_anchor_v1`、`sound_counter_origin` / `sound_effects_counter_origin_v1`；两键取值表达式相同（同值别名）。
- `*-raw` 已成体系（`engine-call-raw`、`particle-shake-raw`、`sound-counter-raw`、`reanimation-raw`、`fp-environment-raw`），表示“逐边界原始旁证”与对应权威字段的配对。
- 同一字符串跨语义位复用共 8 处：`no_game_tick`/`step_count_mismatch` 同时是 error.code 与 stop_reason；`dedup_storage_failed` 还是 status.state；`recording_closed`、`render_failed`、`app_update_anchor_failed`、`mj_clock_anchor_failed`、`sound_counter_origin_failed` 同时是 audit 事件 kind。
- 能力模式名目前只有 `_v1` 一代（全仓无 `_v2+` 能力名）；唯一的版本递增先例是 schema `lvz.launch-windows.v2` → `.v3`（见 §7.5）。

## 7. `_v1` 升级规则

### 7.1 必须升版本（语义/比较范围变化）

- 语义变化：同一模式名/字段名下的含义改变（例：把 calls 从绝对累计改为实验相对计数时必须新声明，而不是改写旧字段）。
- 比较范围变化：可比字段集合、比较对象或采样范围改变（先例 lvz.launch-windows.v2 → .v3：宿主内采样改为子进程隔离采样，新增 observer/isolation 语义并重定义 sampling.scope）。
- 必需字段增删：新增会让旧读取器误判的必需字段，或删除/重命名已发布的必需字段。
- 判定规则变化：旧记录在新规则下被判通过/失败的程度改变（尤其把“未验证”提升为“通过”）。
- 同一名字承载不同可比对象：无法用可选附加字段表达，只能换名加版本。

### 7.2 只是改名（不升版本）

- 拼写/风格统一（initial_mj_clock_anchor_v1 → mj_clock_anchor_v1、sound_counter_origin → sound_effects_counter_origin）。
- 同一概念在能力名与 schema 名之间建立 1:1 映射（branch_scope_v1 ↔ lvz.branch-scope.v1）。
- 注释、文档、内部变量/函数名变化。
- 新增别名键（同一能力同时给出 x_v1 与 x）而不改变任何已发布字符串的含义。

### 7.3 改名时必须遵守的既有硬约束

- 本仓库硬规则：旧档不重写、旧失败不升级为通过（docs/implementation-board.md、docs/engine-replay.md）。已封存证据里的字符串改名等于证据字节变化，因此改名必须同时提供“旧名 → 新名”显式映射，并保留旧名可读。
- 改名不得跨命名空间偷换风格：能力/模式名 snake_case + _vN，schema 名 lvz.<kebab>.vN，错误码 snake_case 且不带版本号。
- 错误码新增是兼容变更（客户端把 code 当不透明字符串）；改变已有码的含义必须换新码名。

### 7.4 读取器遇到未知版本/未知名时的行为

现状（已实现）：

- 能力/模式未知：runtime 只在 capabilities 里公布自己实现的能力，客户端按能力键判定是否使用某模式（sound_effects.py:67、fp_environment.py:54、initialization.py:26）。未公布即视为不支持。
- schema 版本未知：全部严格拒绝。declared_branch_scope() 对 schema != lvz.branch-scope.v1 抛 ProtocolError（tests/test_client.py:215-222 用 lvz.other.v1 做负例）；virtual_audio.py:435-436 对未知事件 schema 抛错；root_integrity/engine_replay/evidence_codec/evidence_tree 对 schema 不符抛 EvidenceError。
- 同族旧版本：允许只读，但只承认该版本明确保证的结论。evaluation.py:643 只对 lvz.launch-windows.v3 取 foreground_check_status，v2 证据一律视为“未验证”而不是猜测通过。
- 错误码未知：客户端把 error.code 当不透明字符串向上抛（client.py:85、engine_replay.py:203-206），不做错误映射，也不猜测重试。

建议（写进后续改名 issue 的验收条件）：

- 能力/模式未知名：fail-closed——不发送该模式的请求，不把旧档追认为该模式。
- schema 未知版本：拒绝解析并保持源文件只读；不得降级归一化、不得删字段、不得就地改写。
- schema 已知旧版本：允许只读并明确标注结论上限（可输出 unverified，不可输出 pass）。
- 错误码未知：按不透明字符串传播，禁止转成成功或静默重试。

### 7.5 先例：`lvz.launch-windows.v2` → `v3`

- v2 由 `24cad37` 引入（宿主内采样的启动窗口证据）；`f9ce28c` 把只读采样搬进拥有者子进程，并在同一提交里新增 v3：`sampling.scope` 从“launch start through initialized return”改为“entire parent context…”，并新增 `sampling.isolation:owned_subprocess` 与 `observer` 溯源块。
- 读取器同步按版本分流：`src/llm_vs_zombies/evaluation.py:643` 只对 v3 取 `foreground_check_status`，v2 证据保持“未验证”；`docs/window-observer.md:40-42` 明确 v3 的判定字段与评测门禁兼容。
- 这是仓库里唯一一次 schema 升版，可直接作为“比较范围变化必须升版本”的判据样板。
