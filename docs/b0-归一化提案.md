# B(0) 归一化提案：`b0_normalization`

日期：2026-09-23。对应 issue [#63](https://github.com/guajun/llm-vs-zombies/issues/63)（`[DESIGN] b0_normalization：把 B(0) 归一化统一成配方声明`）。相关：[#62](https://github.com/guajun/llm-vs-zombies/issues/62)（固定目标 `mj_clock` 已实现）、[#64](https://github.com/guajun/llm-vs-zombies/issues/64)（`app_update_count` 声明式改造，进行中）、[#57](https://github.com/guajun/llm-vs-zombies/issues/57)（[并行实验约定](并行实验约定.md) §2.5.1 已预留本文接口）。

范围声明：本文是**设计提案**。它不启动游戏、不改任何代码、不改既有文档与历史归档、不改写任何失败结论。文中"现状"按本检出的基线 `dd06f16`（`feat(determinism): fixed-target B(0) anchor for LawnApp+0x838 (#62)`）读取；每条判断给到文件与行；没有直接证据的判断标 **[待核实]**。唯一例外是 [并行实验约定](并行实验约定.md) §2.5/§2.5.1：它由 `#66` 在本文写作期间合入根仓库（`e372369`），本文对该文件的引用行号按 `e372369` 计；本条已核，非待核实项。

## 0. 摘要

把"每个字段一个能力、一个 RPC、一条 revision"的做法，换成**一张声明式表 + 一次应用 + 一个回执**：

| 交付点 | 一句话 |
|---|---|
| 形状 | `b0_normalization: [{field, target, reason}, ...]`，`field` 是 B(0) 状态的 JSON Pointer，`target` 是实验声明的固定值，`reason` 是审阅文本 |
| 一次性 | 一个 epoch 只应用一次，整表只消耗一个 revision；表是无条件真实写入，不做比较器偏移、不删字段 |
| 单一回执 | `before`/`after` 逐项给出真实原值与读回值：表内每条 `after == target`，`after_state` 除表内字段外与 `before_state` **逐叶子**相同 |
| 缺省 | "未声明"不再等于"用本 run 观测值"：runtime 声明了能力而计划/配方没给目标时，在发出任何初始化请求前失败 |
| 完整性 | 每个状态字段必须被 **声明 / 记录 / 派生 / 归一化表 / 显式不覆盖** 之一认领；用集合差把"没人认领"的字段判为漏洞 |
| 迁移 | `mj_clock`（已实现）与 `app_update_count`（#64）各自并入同一张表；旧计划、旧配方、旧归档继续按旧形状读，不自动升级 |

### 1.2 两套目标语义

| 字段 | 源 run | 冷重放 | 结果 |
|---|---|---|---|
| `app_update_count` | 不声明目标，写本 run 的真实值，并把它记进配方（`initialization.py:180,230-232`） | 读源配方，把源的实际值写进去（`evaluation.py:690-692`） | 世界内拉平；跨世界各自 1307 / 1340（`docs/平行世界C-D差异报告.md` §3.1） |

## 2. 统一形状

### 2.1 计划、配方、RPC 与回执

计划（`plan.json`，`schema: lvz.evaluation-plan.v2`）：

```json
{
  "schema": "lvz.evaluation-plan.v2",
  "tier": "smoke",
  "seeds": [42],
  "audio_mode": "sound_effects_allocation_none_v1",
  "b0_normalization": [
    {"field": "/sound_effects/app_update_count", "target": 2048,
     "reason": "B(0) 前 App 循环圈数决定，跨世界不可比；C/D 实测差 33"},
    {"field": "/app/mj_clock", "target": 2048,
     "reason": "同一循环的绝对计数，舞者相位直接读它"}
  ]
}
```

配方（`initialization-recipe.json`，与计划同序）：

```json
{
  "b0_normalization": {
    "configuration": { "...": "hello.game.b0_normalization 的逐字段副本" },
    "entries": [
      {"field": "/sound_effects/app_update_count", "target": 2048, "reason": "..."},
      {"field": "/app/mj_clock", "target": 2048, "reason": "..."}
    ]
  }
}
```

配方块的形状沿用现有约定：`configuration` 必须与运行时声明**逐字段相同**（现在的 `sound_effects.same`，见 `app_update_anchor.py:59-62`、`mj_clock_anchor.py:71-73`），这样版本随能力声明绑定。

RPC 与事件：

```text
method  b0_normalization
params  {"entries": [{"field": ..., "target": ..., "reason": ...}, ...]}  + 精确 expect
event   成功 b0_normalized        失败 b0_normalization_failed
B(0)    observation.b0_normalized == true（逐条真实值在回执里，不在观察里重复）
```

回执（`lvz.b0-normalization.v1`）：

```json
{
  "schema": "lvz.b0-normalization.v1",
  "mode": "initial_b0_normalization_v1",
  "requested": [{"field": "...", "target": 2048, "reason": "..."}],
  "before":    [{"field": "...", "value": 1307}],
  "after":     [{"field": "...", "value": 2048}],
  "before_state": { "...": "完整 B(0) 捕获状态" },
  "after_state":  { "...": "同上，除表内字段外必须逐叶子相同" },
  "before_version": {"epoch": 3, "tick": 0, "revision": 6},
  "after_version":  {"epoch": 3, "tick": 0, "revision": 7}
}
```

`before_version`/`after_version` 由 controller 在原生回执上补齐，做法与 `runtime/controller.cpp:586,622` 相同；事件载荷形如 `{request_id, normalization: <回执>}`。

### 2.2 字段语义与约束

| 键 | 类型 | 约束 | 拒绝条件（fail closed） |
|---|---|---|---|
| `field` | 字符串 | 严格 JSON Pointer，指向 B(0) 捕获状态的**整数叶子**；必须属于 runtime 声明的字段集合（见 §2.4） | 指向容器/字符串/浮点原始位/摘要字段；不在声明集合内；同一表内重复出现；解析不出任何字段 |
| `target` | 整数 | `0 <= target <= 2147483647`，`type is int`（布尔与浮点拒绝） | 缺失、`null`、越界、布尔、浮点（沿用 `app_update_anchor.py:26-29`、`mj_clock_anchor.py:37-40`、`evaluation.py:104-105`） |
| `reason` | 字符串 | 非空、不超过 200 字符、不含换行/控制字符；供人审阅并在报告中原样打印 | 缺失、空串、超长；**不参与**跨世界身份（见 §5.5） |

### 2.3 一次性应用与次序

| 规则 | 内容 | 依据 |
|---|---|---|
| R1 声明序即执行序 | 数组次序就是应用与回执次序；读取器拒绝顺序不同的回执 | 新增；与现有"配方块与声明逐字段相等"的写法一致（`app_update_anchor.py:55-62`） |
| R2 一字段一条 | 同表内 `field` 不得重复；表项总数 ≥ 1（空表见 §3.5） | 新增 |
| R3 表内依赖必须可满足 | 有的字段要求别的字段先落地（例：现行 `mj_clock_anchor` 要求 App 锚点已完成，`controller.cpp:606`）。统一后这类依赖写成表项间的有序依赖，声明序必须满足它；不满足或无法判定即拒绝 | `controller.cpp:604-608`；`mj_clock_anchor.py:175-181` |
| R4 无条件写入 | 即使原值恰好等于目标也要执行那次写入并消耗一次性操作，避免"某个世界恰好相等"造成 revision 或事件数不同 | `docs/app-update-anchor-native.md:28-33` |
| R5 整表一个 revision | 一次 `b0_normalization` 只加一次 revision；相对现状（App 锚、MJ 锚各占一次，`controller.cpp:585,621`）少一次 | 新增；epoch/tick 0 的初始 revision 偏移映射不变（`docs/engine-replay.md:219`） |
| R6 非原子声明 | "一次性"指同一 epoch、同一 revision、同一回执，**不是**事务/原子性承诺；中途失败按 §2.5 保留部分写入并冻结 | 与 `controller.cpp:577-580,613-616` 同款处置 |

### 2.4 运行时声明的字段集合

`hello.game.b0_normalization` 沿用现有 SPEC 写法（`mj_clock_anchor.py:24-29`、`app_update_anchor.py:14-18`）扩充为字段表：

```json
{
  "mode": "initial_b0_normalization_v1",
  "available": true,
  "phase": "after_seed_before_warm",
  "requires_audio_mode": "sound_effects_allocation_none_v1",
  "once_per_epoch": true,
  "ordering": "declared_order",
  "fields": [
    {"field": "/sound_effects/app_update_count", "native": "LawnApp+0x484",
     "value_range": [0, 2147483647], "requires_events": ["rng_seeded", "sound_counter_origin_bound"]},
    {"field": "/app/mj_clock", "native": "LawnApp+0x838",
     "value_range": [0, 2147483647], "requires_events": ["rng_seeded"],
     "requires_entries": ["/sound_effects/app_update_count"]}
  ],
  "original_engine_bitwise_unmodified": false,
  "live_verified": false
}
```

`fields` 是**封闭集合**：计划写了集合外的字段就拒绝（对应现状 `initialization.py:120-121` 对"运行时没有该能力"的处理）。`caps` 里必须同时声明 `initial_b0_normalization_v1` 与 `b0_normalization`，且与声明一致（`mj_clock_anchor.negotiate` 的写法，`mj_clock_anchor.py:56-63`）。新增字段的 native 写入器规格尚未定义，首版 `fields` 只应包含 §1.1 的两个字段 **[待核实]**。

### 2.5 单一回执的读取规则

| # | 检查 | 内容 |
|---|---|---|
| 1 | 形状 | 键集合精确相等（沿用现有回执的 set 相等风格，`mj_clock_anchor.py:81-85`）；`requested` 与配方的 `entries` 逐项相等（`field`/`target`/`reason` 一字不差）；长度 ≥ 1；无重复 `field` |
| 2 | 范围 | 每个 `target` 在 `0..2147483647` 且为整数 |
| 3 | 表内 | `after[i].value == requested[i].target`；`before[i].value` 等于 `before_state` 在 `field` 处的实际值 |
| 4 | 表外 | `after_state` 与 `before_state` **逐叶子**比较时只允许表内字段不同；不得用摘要相等代替（`tools/compare_worlds.py:137-155` 的展开口径） |
| 5 | 时间 | `tick == 0`、同 epoch、`after_version == before_version` 只加一次 revision；warm 必须是回执的紧邻下一 revision |
| 6 | RNG | `before_state.rng.instances` 必须与最近的 `rng_seeded` 事件逐项相符（现有校验：`app_update_anchor.py:108-110`、`initialization.py:52-60`） |
| 7 | 前置状态 | `app.ui == 3`、`draw_schedule == {warm_frames:0, step_frames:0}`、无已进入受控引擎调用（`mj_clock_anchor.py:101-107`；`controller.cpp:568-571`） |
| 8 | 序列 | 缺失、重复、晚到、失败事件、声明序不符、锚定后再 `rng_seed`/`rng_restore`/`clock_restore` 都使严格证据失败（`mj-clock-anchor-native.md:137`；`controller.cpp:649-654`） |

回执证明的范围是**已捕获状态**：`before_state`/`after_state` 是 native 捕获（`determinism/audit.cpp:423-463`），未捕获的进程内状态不在证明内（`coverage.complete_game_state=false`，`docs/determinism.md:76`）。

### 2.6 失败、重试与冻结

| 情形 | 行为 |
|---|---|
| 前置拒绝（能力/范围/次序/未播种/未绑定计数原点/已 warm） | 不写内存、不消耗 revision；可用新请求 ID 重试（同 `controller.cpp:568-572,604-608`） |
| 写后校验失败 | 保留已发生的部分写入与完整 before/after 证据，revision +1，记录 `b0_normalization_failed` 并冻结；不回滚、不重试（同 `controller.cpp:577-580,613-616`） |
| 同 ID 同内容重试 | 由现有磁盘日志/journal 返回原回执，不重复写入（`controller.cpp:423-430`） |
| 同 ID 不同内容 | `request_id_conflict`（同上） |
| 成功之后 | `rng_seed`/`rng_restore`/`clock_restore` 封口（`controller.cpp:649-654`；`mj-clock-anchor-native.md:137`） |

### 2.7 非目标

不做比较器偏移、不做字段容差、不删除任何比较字段、不引入"忽略字段清单"、不重写旧归档、不把未覆盖字段塞进表里充数、不使用运行时当场读到的值充当目标（`mj-clock-anchor-native.md:74-75` 的既有立场保持不变）。

  --b0-normalize '{"field":"/sound_effects/app_update_count","target":2048,"reason":"B(0) 前 App 循环圈数"}' `
  --b0-normalize '{"field":"/app/mj_clock","target":2048,"reason":"舞者相位绝对计数"}'

计划命令不启动游戏，因此它**只能**把声明写进文件，不能校核 runtime 是否声明了能力；能力校核发生在 `run`/`start`（`initialization.py:102-121`）。旧版写出的 `"mj_clock": null` 计划仍然是"未声明"（§5.3）。

### 3.3 多字段与顺序

以 C/D 场景为例：两侧真实值都是 1307 / 1340，声明同一目标 2048。执行序必须是"先 App 计数、后 MJ 计数"，因为现行 MJ 锚点的前置条件就是 App 锚点已完成（`controller.cpp:606`；读取器对应检查 `mj_clock_anchor.py:175-181`）。统一后这一依赖变成**表内依赖**：两条表项在同一次 `b0_normalization` 里按声明序落地，`app_update_anchor.semantics(pending_mj_clock=True)` 的临时掩码（`app_update_anchor.py:134-150`；`engine_replay.py:910-913`）随之删除。

顺序不成立、或声明序无法同时满足所有依赖时，属于**前置拒绝**（不写、不消耗 revision），而不是"写一半再报错"。

### 3.6 与 `clock_restore` 的边界

`clock_restore` 是**记录型**操作：把本 run 在 B(0) 前记录的三时钟快照恢复回来，让同一世界的冷重放复现自己；`b0_normalization` 是**归一化**操作：把跨世界不可比的字段真实写到同一个声明目标。两者都写真实内存、都不删字段、都不做偏移（`docs/determinism.md:40`）。

| 维度 | `clock_restore`（记录型） | `b0_normalization`（归一化表） |
|---|---|---|
| 目标来源 | 本 run 记录的 `clock_anchor` 快照（`initialization.py:40-44,143-148`） | 实验声明的固定目标 |
| 目的 | 世界内可复现 | 跨世界可比 |
| 写入点 | 三地址同时写：`board+0x5568`（GameClock）、`board+0x556c`（EffectCounter）、`app+0x838`（MjClock）（`determinism/audit.cpp:415,418-419`） | 只写表内声明的字段 |
| 时机 | `rng_seed` 之后、归一化之前（`docs/engine-replay.md:267,277`；`mj-clock-anchor-native.md:116`） | 计数原点/App 锚点之后、warm 之前 |
| 封口 | 与 `rng_seed`/`rng_restore` 一起在一次性锚定后被拒（`controller.cpp:649-654`） | 以自身成功封口；之后再 seed/restore 一律拒绝 |
| 配方痕迹 | `clock_anchor`、`postwarm_clock` | `b0_normalization.entries` + `b0_normalized` 事件 |

同一地址（`/app/mj_clock`）两个阶段都会写，规则固定为：**先恢复记录值、后写共同目标**；因此配方里 `clock_anchor.mj_clock` 是恢复后的真实值（各世界可以不同，C/D 就是 1307/1340），`postwarm_clock.mj_clock` 是归一化后的声明目标（`initialization.py:225,254,260-268`；`docs/平行世界C-D差异报告.md:76`）。warm 回执仍要求 `clocks_before == clocks_after == 配方值`（`initialization.py:254`）。

两条禁止：归一化不得改名冒充 `clock_restore`（`rng_seed`/`clock_restore` 封口规则不变）；归一化也不替代 `clock_restore`——缺该能力的 runtime 在需要恢复时仍拒绝（`initialization.py:122-123`）。

### 4.1 五类划分

### 4.3 集合差做法（可落地）

输入是**已封存 run 的 B(0) 标记**，全程只读、不启动游戏：

1. 取 B(0)：`observations/initial-audit.json` 与 `audit/state-deltas.jsonl` 首条（写入点 `initialization.py:293-296`；文件语义 `docs/determinism.md:62-64`），版本必须等于 marker 的 `observation.version`（`initialization.py:274-276`）。
2. 枚举叶子 `U`：按 JSON Pointer 规则展开（复用 `tools/compare_worlds.py:101-118,137-155` 的指针转义与数组下标口径），对象/数组展开到标量；空对象、空数组记为自身。
3. 读五类集合：`declared`（§4.2 的声明项）、`recorded`、`derived`、`normalization`（`b0_normalization.entries[*].field`）、`uncovered`（配方声明的边界项）。每类是一组**指针模式**（精确路径，或含 `*` 段的模式，如 `/zombies/slots/*/fields/0000002c`）；展开成同一 pointer 空间里的 `C_declared … C_uncovered`。
4. 取并集 `C`，做**两个方向**的差：
   - 漏洞 `H = U \ C`：状态里存在、五类都不认领；
   - 悬空 `D = C \ U`：声明了但 B(0) 里不存在（通常是拼写错误或版本不一致）。
5. 冲突检查：`normalization ∩ uncovered = ∅`（同一字段不能既声明"不写"又写）；`normalization` 每条必须命中恰好一个整数叶子；`derived` 每条必须附重算/映射的实现位置，否则并入 `H`。
6. 输出与失败：报告写 `coverage_complete: (H==∅ and D==∅)`、B(0) 版本与两侧摘要、`len(U)`、五类计数，以及 `H`/`D` 的样本（每类最多 50 条 + 总数，只截断显示、不截断判定）。任一非空即**严格证据失败**（沿用 `audit_compare.EvidenceError` 的口径，`audit_compare.py` 的 `fail` 系列），不得只告警；两个世界合并前各自跑一遍，再对"两侧叶子的并集"跑一遍。

### 4.4 边界与反例

| 边界 | 规则 |
|---|---|
| 动态叶子 | 池的 `slots` 键随 `used` 变化（`determinism/audit.cpp:196-205`）、卡槽数量随 `count` 变化（`audit.cpp:209-222`）、波表只写已声明行（`audit.cpp:443-446`）——模式必须用 `*` 覆盖整个键空间；检查按**本次 run 的实际 B(0)** 跑，不假设上一份 run 的叶子集合 |
| 可选结构 | `sound_effects` 仅显式静音模式存在（`audit.cpp:433`），`challenge` 可能为 `null` 值（`audit.cpp:458-459`）——模式自带 `required`/`optional` 标记，`optional` 允许命中零个叶子；可选性由 runtime 声明，不由配方自定 |
| 检查范围 | 正式范围是 B(0)；B(0) 之后每帧的叶子并集是否纳入同一检查属后续工作 **[待核实]** |
| 与 `coverage.uncovered` 一致 | 配方里的"显式不覆盖"必须逐条对上 `audit/manifest.json.coverage.uncovered`；交集不为空即拒绝，避免"把写了的字段洗成不覆盖" |
| 与读取点表一致 | 一个字段能不能进"显式不覆盖"，要看 `docs/机制读取点表.md` §1.1-1.4 的（字段, 读取点）结论：标着进 S 的读取点不能只写一句"不覆盖"了事 |
| 不能夸大的结论 | 该检查只说明"**已捕获状态**内没有未分类字段"；`coverage.complete_game_state=false` 不变（`docs/determinism.md:76`） |

### 5.5 与根身份、合并校验的关系

- 根身份把 `init_recipe` 原样纳入（`evidence_tree.py:94-114`；`docs/并行分支worker.md:44,50`），因此**表必须进身份，`reason` 不能进身份**：构造根身份前把 `entries` 投影成有序 `(field, target)` 对。否则同一目标只因措辞不同就会产生两个"根"，把可合并的世界判成不可合并。
- 联合报告（`docs/并行实验约定.md:157-159`）新增一行：`b0_normalization.entries` 投影后的 `(field, target)` 序列必须全等；`reason` 并排打印给审阅，不作等同判据。
- `reason` 仍受 run 自身约束：它写在 `initialization-recipe.json` 里，而该文件的 SHA-256 绑定在 manifest（`initialization.py:74,83-89`），事后改写会破坏封包校验。
