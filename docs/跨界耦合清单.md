## 0. 摘要

**一句话结论（按合同 §3.4 顺序）**：

| # | 合同条目 | 结论 | 状态分布 |
|---|---|---|---|
| 1 | 时间源 | 只有 `GetTickCount`、静态 CRT 的 `_time64`（RNG/Board 播种）与 `time`（版本检查阈值）有**进控制流**的读点；前两者在锁定配方下已覆盖，`time` 的目标分支未实测；`QueryPerformanceCounter`/`QueryPerformanceFrequency`/`GetSystemTimeAsFileTime`/`GetLocalTime` 在导入表里存在但候选源码内没有调用点 | 已固定 5 / 已证伪 2 / 待定 4 |
| 2 | 音频设备状态 | `IsPlaying` 返回值已**实测**进控制流（036 事故），当前靠 `sound_effects_allocation_none_v1` 切在源头；音乐/BASS 与设备枚举未虚拟化 | 已固定 1 / 待定 2 |
| 3 | 光标 / 焦点 / 窗口消息 | 引擎自己只查 `GetActiveWindow`（已被启动器按进程重写），**不查** `GetForegroundWindow`；真实桌面焦点/激活/光标扰动未做 | 已固定 2 / 已证伪 1 / 待定 5 |
| 4 | 文件与日志游标、CRT `FILE*` 缓冲 | 存档**内容**进控制流且属根身份；写盘缓冲与内核文件游标在 a2 恢复路径上不可回滚 | 已固定 4 / 待定 2 |
| 5 | 并行时的共享设备、用户档与目录 | 互斥体、用户档、注册表、运行目录、Job 已按 run 隔离；共享音频设备与磁盘/CPU 竞争未通过并行验收 | 已固定 5 / 待定 2 |
| 合计 | 35 条 | —— | 已固定 17 / 已证伪 3 / 待定 15 |

四条值得单独记住的结构性事实：

1. **"进控制流"的时间读点只有三处**：`mRandSeed = GetTickCount()`（全局 MT 种子）、`srand(GetTickCount())`（游戏线程 CRT 种子）、静态 CRT `_time64(nullptr)` → `LawnApp::mAppRandSeed` → `Board::mBoardRandSeed`（Board 局部 MT 种子），另有 `time()` → 版本检查阈值比较（C35，目标分支未实测）。其余 `GetTickCount`/`timeGetTime` 读点目前只用于 FPS、加载时长、日志与屏幕保护判定。
2. **导入表存在 ≠ 被调用，导入表缺席 ≠ 不被调用**：`QueryPerformanceCounter` 有导入槽却找不到调用点；`_time64`/`time` 没有导入槽（静态 CRT）却几乎肯定被调用；`DirectSoundCreate`、`BASS_*`、`GetLastInputInfo` 都靠 `LoadLibraryA` + `GetProcAddress` 解析，导入表里根本不会有。三类证据必须并列，不能互相替代。
3. **外层 wrapper 不是我们的运行时**：`game/original/PlantsVsZombies.exe` 会解包并启动内层引擎 `popcapgame1.exe`（`docs/determinism.md`）；本项目启动器直接运行内层引擎（`docs/launcher.md`）。两者导入表不同——例如 `GetForegroundWindow` 只出现在 wrapper 里。
4. **启动器已经在做 IAT 级接管**（`launcher/bootstrap.cpp`）：按导入名重写主 EXE 的 `FirstThunk` 槽，正是探针 B（虚拟时钟）要复用的最小落地机制；不需要新的注入方式。

## 1. 方法与词表

### 1.1 三种来源

| 来源 | 含义 | 本次实际用到 |
|---|---|---|
| **静态导入表** | 目标 PE 的 `IMAGE_DIRECTORY_ENTRY_IMPORT` / `DELAY_IMPORT` 描述符中出现的名字，含 IAT 槽的 VA。只能证明"被引用了这个名"，不证明调用、不证明返回值进入控制流 | `tools/import_scan.py`（§2） |
| **动态调用点** | 具体 `文件:行号` 的读取点；本次全部来自候选反编译副本 `work/replay-research/`（PvZ 1.0.0.1051，固定提交 `8a2d1218`），与既有文档的 `[源码]` 同级：**未逐条反汇编** | §3 各条的 `read_sites` |
| **既有实测** | 项目已归档的运行观测（含原生机器码级复核）。本文只引用，不新增 | 041/043/044/047/048/050 等记录 |

补充口径沿用 `docs/机制读取点表.md` §1.4：`[源码]` 为候选副本证据，`[实测]` 为已归档观测，`[推断]` 为由源码或实测推出、尚无直接观测。

### 1.2 状态词表（三条，互斥）

| 状态 | 判定门槛 | 反例（不构成该状态） |
|---|---|---|
| **已固定** | 存在已实现并被证据支持的机制，使该输入不再成为自由度；必须写明前提条件 | "我们没跑过它出事" |
| **已证伪** | 有证据表明该耦合**在本目标上不可达**（例如三个扫描文件的导入表与原始字符串都查不到该名），或已有实测表明其变化不进入 S | 只因为"没观察到差异" |
| **待定** | 其余全部情形，包括"机制成立但后果未实测""有导入槽但找不到调用点""观测器未采集到有效样本" | —— |

本次的 `已证伪` **全部是"静态不可达"这一种含义**，即证据来自静态扫描并已标明其边界（不覆盖运行期动态解析与静态 CRT 内部实现）；本项目**没有**任何一条因"实测未发现差异"而升级为已证伪。

### 1.3 控制流关系词表（回答"返回值进入控制流还是仅作输出"）

| 取值 | 含义 | 对 S 的意义 |
|---|---|---|
| `enters_control_flow` | 返回值参与**比较/选择**、**算术**或**随机消费**（合同 §2.1） | 必须进 S 或被固定 |
| `output_only` | 返回值只用于显示、日志、诊断、统计，不参与以上三者 | 不进 S（但可能把墙钟带进日志，见 C08/C27） |
| `unresolved` | 有读取点但本次无法判定其角色（缺少调用点或缺少观测） | 待定项的统一取值 |

**逐条都给出该字段**：例如 `GetTickCount` 在播种读点是 `enters_control_flow`，在 FPS/日志读点是 `output_only`；同一个 API 因此可能出现在多行（合同 §2.2 的分析单位是读取点，不是字段）。

### 1.3.1 本清单的三条不变式

1. 同一 API 的不同读取点分别定级；不给 API 整体下结论。
2. 任何"已固定"必须写出前提（模式、配方、存档、构造方式），因为本项目的固定手段依赖运行配置。
3. 任何"已证伪"必须写出证据类型（静态/实测）与未覆盖面。

### 1.5 复现命令

```powershell
# 在仓库根运行；只读文件，不加载、不执行目标
python tools/import_scan.py --strings `
  --json work/import-scan.json --text work/import-scan.txt `
  game/original/PlantsVsZombies.exe game/local-engine/PlantsVsZombies.exe game/original/bass.dll

# 只看某一族，或换成任意 PE
python tools/import_scan.py --families time,audio game/local-engine/PlantsVsZombies.exe
```

退出码：全部文件解析成功为 `0`，任一文件不是可解析的 PE 或不存在为 `1`，族名非法为 `2`。工具从不 `LoadLibrary`、从不启动进程、从不写目标文件。

### 1.6 静态导入表的两个盲区（决定了本文为什么必须并列三种来源）

1. **静态 CRT**：引擎的导入 DLL 列表里没有 `MSVCRT.dll` 或其它 CRT（三个文件里只有 `bass.dll` 带 `MSVCRT.dll`），据此推断引擎与 CRT 静态链接 `[推断]`。`time` / `_time64` / `clock` 因此不会出现在任何导入表里，候选源码却明确调用 `_time64`（C03）。这类调用只能靠内联补丁或调用点追踪覆盖。
2. **运行时解析**：`SexyAppFramework_SexyAppBase.cpp:142-145` 用 `LoadLibraryA` 取得 `version.dll`/`ddraw.dll`/`dsound.dll`，再用 `GetProcAddress` 取 `DirectSoundCreate`、`GetLastInputInfo`；`DSoundManager.cpp:46-49` 同样动态取 `DirectSoundCreate`；音乐侧 `BASS_*` 同理（引擎导入表里只有 `BASS_*` 的**原始字符串**，没有导入槽）。这些名字在导入表里必然缺席。

## 4. 探针 A：长挂起 vs 短挂起

**要回答的问题**：在已完成的稳定边界上让墙钟前进 T 秒（期间进程是否被冻结是两个不同的实验），是否改变捕获状态、是否改变后续轨迹。

合同依据：`docs/分支数据合同与实施计划.md` §3.3 的 R2/R3/R4（"恢复后推进 1 tick / N tick / 改恢复间隔、主机负载、并行度"）与 `docs/原版确定性重放器提案.md` §5 的 P3（分别改变暂停时长、窗口焦点、渲染频率、日志开关）。`docs/determinism.md` 已明确要求："暂停和隐藏窗口可能继续消耗共享随机流，必须进行扰动验收。"

### 4.1 现有基线证据（已归档，全部通过）

| 观测 | 结果 | 出处 |
|---|---|---|
| `headless-launch-006`：间隔一秒的完整已审计快照相同 | 通过 | `docs/headless-validation.md:12` |

## 5. 探针 B：虚拟时钟

**要回答的问题**：把 `GetTickCount`/`GetTickCount64`/`QPC`/`QPF`/`time`/`_time64` 固定或按 tick 推进后，是否还有墙钟影响进入 S；反过来，把虚拟时钟按不同速率推进时，捕获状态是否随之变化（**威力检查**）。

设计参考：`docs/libTAS与AvZ方案调研.md` §2.3（libTAS 把主线程 `clock_gettime`/`gettimeofday`/`time` 与 Wine 侧 `GetTickCount`/`GetTickCount64`/`QueryPerformanceFrequency`/`QueryPerformanceCounter` 全部接管，时间只在帧边界按 1/fps 推进）与 §2.8（Wine 补丁点清单）；本项目只借机制，不迁移到 Wine。

### 5.1 三段式：先观察，再固定，再推进

| 阶段 | 做什么 | 通过判据 |
|---|---|---|
| **B0 只观察** | 在每个已知 IAT 槽后面接计数/记录 thunk，返回原值不变；记录 `(调用序号, 调用线程, 返回地址 RVA, 返回值)` 到 native 旁证 | 记录完整、不改变任何捕获状态；得到"哪些函数真的被调用、调用频次、调用线程"的实际清单 |
| **B1 固定** | `GetTickCount`/`timeGetTime` 返回配方常量 `base_ms`；`QPF` 返回固定常量；`QPC` 返回 `base_ms * qpf / 1000`；`time`/`_time64` 返回固定 unix 秒 | 两次不同墙钟起点的冷重放逐帧相等，且虚拟时钟读点 trace 逐项相等（见 §5.4） |
| **B2 按 tick 推进** | 每次受控引擎调用边界把虚拟毫秒 +10（与 `SECONDS_PER_UPDATE = 0.01f` 对齐），`QPC` 同步推进；宿主侧 IPC/日志/观察器仍用真实时间 | 同上；且与 B1 的差异只出现在**确实读取**虚拟时钟的字段上，可逐条归因 |

B0 是 #12→#13 的既有节奏（先用纯观察探针定位因果，再改语义），不得跳过。

### 5.2 最小落地方式

1. **IAT 槽重写（首选）**，复用 `launcher/bootstrap.cpp` 的既有机制：遍历主 EXE 的 `IMAGE_IMPORT_DESCRIPTOR`，用 `OriginalFirstThunk` 的 `IMAGE_IMPORT_BY_NAME` 按名匹配，`VirtualProtect` 临时开放写权限后改写对应 `FirstThunk` 槽，主线程恢复前完成。本轮扫描给出的确切槽位：

| 函数 | 提供者 | 引擎 IAT 槽 VA |
|---|---|---|
| `GetTickCount` | KERNEL32 | `0x65208c` |
| `QueryPerformanceCounter` | KERNEL32 | `0x652088` |
| `QueryPerformanceFrequency` | KERNEL32 | `0x652084` |
| `GetSystemTimeAsFileTime` | KERNEL32 | `0x652190` |
| `GetLocalTime` | KERNEL32 | `0x6521a8` |
| `timeGetTime` | WINMM | `0x652400` |

   这些 VA 只对 `f9669af3…1322`、镜像基址 `0x400000` 的这份引擎有效。落地时必须像 `docs/silent-audio.md` 描述的前置校验那样，先核对文件 SHA-256、PE 头/`SizeOfImage`，再核对**槽内当前值**等于 `GetProcAddress` 得到的真实函数地址，全部匹配才写；任一条不符即 fail closed。

2. **静态 CRT 的例外**：`time`/`_time64`/`clock` 没有导入槽（§1.6），必须走内联补丁，或先按有界签名定位调用点——至少包括 `LawnApp` 构造路径的 `_time64`（C03）与 `SexyApp::CheckForUpdatesNeeded` 的 `time`（C35）。定位失败时必须显式声明"未覆盖"，不允许静默跳过。

3. **线程与作用域**：thunk 只在**游戏线程**且处于受控边界内返回虚拟值，其它情况转发真实函数。宿主侧（IPC 超时、日志时间戳、窗口观察、证据封存）必须继续用真实墙钟——它们的语义依赖真实时间，且不属于 S。

4. **数值映射与记录**：`base_ms`、`qpf`、虚拟 unix 秒都是配方常量（不取自启动时刻），连同 thunk 目标地址、原槽值、目标文件哈希写入 manifest/hello 与初始化配方；虚拟时钟自身的读取轨迹作为 native 旁证与状态摘要同源落盘。

5. **能力声明**：新增 `capabilities.virtual_clock_*` 与 `game.time_source.mode`，与 `deterministic_draw_schedule_v1`、`sound_effects_allocation_none_v1` 一样属于**改变实验语义**的可选模式：旧档不能被追认为该模式；启用该模式的记录必须新录源、重新做冷重放验收。

### 5.4 判定标准

**通过**（全部满足）：

1. **读点清单**：B0 给出被真实调用的函数、频次、调用线程与调用点 RVA；至少覆盖 §3.1 的 C05–C07 与 C03 涉及的 CRT 路径。任何"未定位调用点"的函数必须在报告里显式列为未覆盖。
2. **可复现**：两次不同墙钟起点的 B1/B2 运行，逐帧捕获状态相等（沿用现有 10,000 边界门槛），且虚拟时钟读点 trace 逐项相等（调用序号、RVA、返回值一致）。
3. **威力检查（必做，不可省）**：把虚拟时钟速率改成 2×（或加固定偏移）再跑一遍。
   - 若捕获状态出现差异 → 该时间源**确实**经某个读取点进入 S：必须定位首个差异并归因到具体读取点；
   - 若整轮捕获状态仍然完全相等 → 只能得出"在当前读取点与当前捕获范围内，该返回值不进入 S"，**不能**升级为 C05–C07 的全局"已证伪"（有限捕获不等于全状态证明）。
4. **宿主侧不受影响**：IPC 超时、日志时间戳、窗口观察采样与证据封存仍使用真实时间，且这些字段不进入比较状态；现有门槛一条不放宽。
5. **不改原版**：与 `silent-audio` 同级，模式声明 `original_engine_bitwise_unmodified:false`，旧档不追认。

**失败**：读点 trace 不完整或与状态摘要不同源；两次运行的 trace 出现差异；威力检查出现未归因差异；thunk 前置校验失败却继续运行。
