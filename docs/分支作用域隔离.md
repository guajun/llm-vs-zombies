# 分支作用域隔离：去重域与版本命名空间

日期：2026-09-22。状态：**已实现（原生 runtime + Python 侧 + 单测）**。对应 issue
[#32](https://github.com/guajun/llm-vs-zombies/issues/32)（N4），依赖 N1
（[分支数据合同与实施计划](分支数据合同与实施计划.md)）与 N3
（[树身份](../src/llm_vs_zombies/evidence_tree.py)）。协议条款写在
[runtime-protocol.md](runtime-protocol.md#branch-scope-and-dedup-namespaces)。

## 0. 问题

runtime 的去重索引是进程内 RAM 桶数组 + 磁盘 append-only journal，键只有
`(epoch, request_id)`。fork / 克隆出的兄弟进程会继承同一份 journal 文件、同一份内存索引
以及同样的 `epoch/tick/revision`，于是它可以用父时间线的缓存回答一个自己从未执行过的请求：
客户端拿到一条协议上完全合法、内容却来自另一条时间线的轨迹。这是训练数据里最隐蔽的一类
污染，因为它在证据层看不出任何异常。

三条危险路径都指向同一处：

1. 内存克隆（`RtlCloneUserProcess`、a2 快照恢复到同一进程）继承索引与版本；
2. 新进程收养父进程留下的 journal 文件（宿主侧"继续跑"）；
3. 客户端把 `request_id` 当成全局唯一，跨分支复用同一个 ID。

## 1. 规则

| 规则 | 内容 |
|---|---|
| **R1 身份** | 每个 runtime 实例恰好拥有一个 `branch_id`，进入 `hello.branch` 与 `status.branch`：`{schema:"lvz.branch-scope.v1", mode, branch_id, parent_branch_id, origin, dedup_key}`；`capabilities.branch_scope_v1=true`，`capabilities.branch_rebind=true`。`origin ∈ {session, adopted, rebound}`。 |
| **R2 去重键** | 去重域为 `(branch_id, epoch, request_id)`。journal 每条记录存下当时的 scope，命中只比较同 scope 记录。scope 声明**不进** payload 身份：runtime 在规范化之前剥掉顶层 `branch`，因此同一逻辑请求在每个分支里逐字节相同。 |
| **R3 请求声明** | 请求可带顶层 `branch`。缺失 = 旧客户端语义（隐式本分支）；与本实例 scope 不符 = 立即 `branch_scope_mismatch`，不执行、不写 journal、不返回他分支结果。 |
| **R4 跨分支同 ID** | 同 ID 记录出现在他分支 scope 时，绝不作为命中：内容相同（剥离 scope 声明后）→ 在本分支执行并绑定，兄弟各得自己的结果；内容不同 → `cross_branch_request_id_conflict`。`status` 查他分支 ID 返回 `request_state:"foreign_branch"` 且不回 `response`。 |
| **R5 版本命名空间** | 完整版本是 `(branch_id, epoch, tick, revision)` 四元组；旧三元组只在单分支 scope 内可比。跨分支或跨代对比必须带 branch，否则一律无效。 |
| **R6 分支切换** | 两条受控路径：(a) 内存克隆 → `branch_rebind{branch_id, from_branch_id, parent_branch_id?}`，必须声明自己正在离开的 scope；(b) 新进程收养 → `JournalOptions.adopt`（`LVZ_JOURNAL_ADOPT=1`），从记录重建索引。记录不重写：旧记录保留原 scope。 |
| **R7 命名与记录** | `branch_id` 语法与 N3 证据树完全一致（`[A-Za-z0-9][A-Za-z0-9._:-]{0,63}`），协议层与证据层的校验器由测试锁定一致。branch 只写进 `hello`/`status`/run manifest/轨迹初始 marker/重放报告，**不进**原生审计 manifest、状态摘要与 draw/engine-call 证据。 |

### 1.1 错误码

| 码 | 触发 | 是否执行 | 是否写 journal |
|---|---|---|---|
| `branch_scope_mismatch` | 请求声明了他分支（或向无 scope 的 runtime 声明 scope） | 否 | 否 |
| `cross_branch_request_id_conflict` | 同 ID 在他分支已绑定不同内容 | 否 | 否 |
| `branch_rebind_rejected` | `from_branch_id` 与当前 scope 不符 | 否 | 否 |
| `invalid_request` | `branch` 字段不是合法 scope id | 否 | 否 |
| `invalid_params` | `branch_rebind` 参数缺失或非法 | 否 | 否 |
| `request_id_conflict`、`dedup_storage_failed`、`dedup_capacity` | 同 scope 内的旧语义，完全不变 | 按旧规则 | 按旧规则 |

## 2. 兼容性矩阵

| 组合 | 行为 |
|---|---|
| 旧客户端（请求不带 `branch`）+ 新 runtime | 隐式使用本实例 scope，语义与旧版一致；同 scope 重试仍返回逐字节相同的旧响应 |
| 新客户端 + 旧 runtime（`hello` 无 `branch`） | 客户端不发送 `branch` 字段，行为与旧版一致；`Client.branch_scope` 为 `None` |
| 旧记录（manifest / 轨迹 / 初始 marker 无 `branch`） | 仍可读、可校验、可重放；`branch` 字段可选，缺省即"未声明 scope" |
| 旧 journal 文件 `LVZREQ01` | 仍是合法归档证据，但不被采纳、不被改写；尝试收养会得到明确错误 |
| 旧原生审计、状态摘要、draw/engine-call 证据 | 完全不含 branch，新旧记录可直接比较 |
| `pause` / `commit` / terminal / close 语义 | 未改动；新方法不进入既有路径，同 scope 的 pausing、终局冻结与封包顺序保持原样 |

## 5. 未做 + 前置条件

1. **真实 fork / 克隆路径未做**：本 issue 提供命名空间规则、`branch_rebind` 与收养协议，真正的
   内存克隆 / a2 快照恢复属 #33（N5）。宿主在克隆后必须二选一：同进程回滚调用
   `branch_rebind`，或新进程设置 `LVZ_JOURNAL_ADOPT=1` 收养父 journal。a2 恢复时的
   `epoch` 传递（`LVZ_JOURNAL_EPOCH`）需要宿主提供父进程当前 epoch，否则默认 1。
2. **未启动游戏、未跑长局**：真实对局下的跨分支隔离未验证。前置条件：冻结的 AvZ 子模块
   可构建 + #33 的分叉能力 + 一个真实 run 目录。
3. **launcher 未注入 `LVZ_BRANCH_ID`**：`launcher/native_launcher.cpp` 尚未传递分支环境变量，
   当前缺省值是"会话目录名 + PID"。要让证据树 `branch_id` 与 runtime 身份一致，需要宿主显式设置
   （属 #33/#35 的宿主接线）。

   **2026-09-24 更新（issue #50 子项 1）**：已在启动器侧接上，原条目文本保留不改。缺省分支名 = run
   目录名（可用 `--branch-id` 覆盖），语法与本表 R7 一致；原生启动器在主线程恢复前校验、注入并把
   `branch_id` 写进 `native-receipt.json`，`launcher.py` 再复核
   `hello.branch.branch_id == 本 run 声明的 branch_id`，不符即停止自有进程。来源、生命周期与兼容性见
   [launcher.md](launcher.md) §分支身份；测试见 `tests/branch_id_tests.cpp`（原生语法）与
   `tests/test_launcher.py::BranchIdentityTests`（身份一致、缺省行为不变、非法/超长失败）。本次只改
   "未做"清单，`LVZ_BRANCH_ID` 缺省回退、旧记录与旧 journal 的兼容口径一字未改；真实游戏上的分支
   身份证据仍待主 agent 串行排产（本节不含真机结论）。
4. **构建环境的两个沙箱限制**：新克隆缺少 `avz/framework` 子模块，本次只读引用了根仓库里同一
   pinned 提交的源码（三份源文件 SHA-256 与 `runtime/avz_overlay.cmake` 的固定值逐一相符）；
   沙箱内 `ninja` 不可执行，改用工具链自带的 `mingw32-make` 作为 CMake 生成器。除此之外的完整
   构建（含 `recorder.dll`）与 `ctest` 全部通过。
5. **并行 worker（#38）不在本 issue**：本实现只保证同一 journal 血统内不串号，不提供多进程
   并发写同一文件的仲裁；收养的前置条件是父进程已释放（退出或关闭）该文件。
6. 未改游戏内 DLL，未触碰 `experiments/` 与 `game/`。
