# 运阵影响分级与读档等价性评估

本文回答三个问题：**哪些状态真正影响运阵**、**原版读档/接管到底保住了什么**、以及
**"阵型级可重复"应当怎样写成可判分的契约**。所有技术结论都标注来源等级：

- **[源码]** 来自 `work/replay-research/`（PvZ 1.0.0.1051 反编译副本）的具体文件:行
- **[社区一手]** 来自 AvZ（AsmVsZombies）固定提交的教程/头文件原文
- **[实测]** 来自本项目已归档的测量数据
- **[文献]** 来自论文元数据（未逐篇通读全文）
- **[推断]** 由上述证据推出、尚无直接观测

---

## 0. 结论摘要

1. **"影响运阵"的状态可以收成三层**：A 阵型层（必须逐字段相等）、B 转移层（不要求相等，但要求
   输入一致——主要是 RNG 与动画时钟）、C 表现层（允许不同，只需记录）。实测中每 tick 变化的
   ~783 个字段里，82.4% 是可重算/派生的量，真正携带玩法信息的只有约 8%。**[实测]**
2. **动画不能整体踢出**，但可以分层：动画**句柄身份**可归一化，动画**进度与速率**必须保留。
   已有取证见 `docs/动画耦合与可重复性取证.md`。**[源码]**
3. **原版存档是"阵型等价"，不是"轨迹等价"。** 它保存了 Board 自 `mPaused` 起的全部字节
   （含波表 `mZombiesInWave`、`mBoardRandSeed`、`mZombieCountDown`），以及 6 个实体数组 +
   粒子/动画/拖尾/附着的内容与**空闲链表**；但**不保存**全局 MT、CRT 随机数状态、`DataArray::mNextKey`
   和 Board 之外的 app 级状态。**[源码]**
4. **社区说的"栈位"就是对象在 `DataArray` 中的编号**，它确实进入玩法判定（同格植物的选择、
   巨人砸击目标预测、1cs 偏差）。**已存在对象的栈位随对象字节一起入档，读档不会重排它们**；
   读档真正改变的是**未来出怪的随机性**（全局 MT 不入档）和**ID 代次（key）重发**。**[源码]+[社区一手]**
5. 因此你的判断成立一半：无尽阵型在"逐帧"意义上确实不是严格研究对象，社区事实上用"阵型/波次级"
   等价在跑；但 A/B 两层必须严格，否则结果不是"不可重复"，而是**不可判分**。
6. **LLM exploit 是真实风险且已有先例可援引**：社区自己的回放实现就是"疯狂存档读档"，其官方文档
   承认补帧"可能会导致数据不一致"；学术侧 2026 年已有测量 LLM agent specification gaming 的成套结果。
   **[社区一手]+[文献]** 这属于评测设计问题，应当用契约 + 红队处理，而不是靠"游戏本身严不严谨"来化解。

## 1. A / B / C 三层分级

| 层 | 判定要求 | 内容 | 主要依据 |
|---|---|---|---|
| **A 阵型层** | 必须逐字段相等，作为"运阵可重复"的判据 | 植物集合与类型/格位/血量/状态；僵尸集合与类型/行/坐标/血量/护具/相位；投射物；格子物品（墓碑/梯子/弹坑/传送门/脑子/耙子）；推车状态；波表 `mZombiesInWave`、`mCurrentWave`、出怪倒计时与血量阈值、`mZombieAllowed`、`mRowPickingArray`；阳光/金币/卡槽冷却；关卡常量 `mBoardRandSeed`/`mLevel`/`mPlantRow`/`mGridSquareType` | `Lawn_Board.h:107-185`；波表在建局时用全局 `Rand` 抽定后写入 Board（`Lawn_Board.cpp:575-800,2528`） |
| **B 转移层** | 不要求相等，但要求"输入一致"：同一 tick、同一输入、同一次 RNG 消费 | 全局 MT 与 CRT 随机流的状态与消费次数；动画时钟（`anim_time`/`anim_rate`/`frame_count`/`loop_*`，因为 `ShouldTriggerTimedEvent(阈值)` 读它）；音效播放状态（`IsPlaying` 会改变"最近播放"准入，从而改变 MT 消费次数）；引擎调用/绘制边界与 App 更新锚定 | `Lawn_Zombie.cpp:973-982`、`Lawn_Plant.cpp` 多处 `RandRangeFloat`；本项目 issue 10/11/12/13/14 的既有验收 |
| **C 表现层** | 允许不同，只需记录 | `overlay_matrix_bits`、`extra_additive_color`、`track_scalars`；由 `mAnimCounter` 派生的 `mFrame`/`mPrevFrame`；纯计时器（`mGroanCounter`、`mJustGotShotCounter`、`mBlinkCountdown`、`mEatenFlashCountdown`）；粒子视觉、splash/flash；**reanimation 句柄的代次数值** | `docs/动画耦合与可重复性取证.md` §4/§6 |

关键警告：C 层的"纯表现"是有条件的。**只要某个表现层对象在创建时消耗了共享 RNG，它就不再是纯表现**——
多一个少一个动画对象会让后续出怪类型和行路整体平移。**[源码]**

## 2. 源码级依据（选摘，可复核）

### 2.1 栈位真的进入玩法判定

- `Board::GetPlantsOnLawn()`（`Lawn_Board.cpp:2175`）用 `IteratePlants()` 遍历，而
  `IterateNext()` 是**按块索引升序**（`Sexy.TodLib_DataArray.h`）。同格多植物时后写入者覆盖，
  于是"谁被吃/被砸"取决于各植物的**编号**。
- 社区侧把这条规则直接写成判定：AvZ 的 `processor.h` 用
  `fodderIdx < pumpkinIdx` 预测"垫材栈位小于南瓜头，南瓜头没事"；`jing_dian_4.cpp` 里多处
  `-298 + 1`，注释为"1 是为了兼容栈位带来的 1cs 偏差"。**[社区一手]**
- `avz_pvz_struct.h` 对僵尸/植物/格子物品/炮弹等对象都给了同一注释：**"对象的编号（栈位）"**，
  字段是 `Index()`，读取 `sizeof(_data) - 4`（或 -8）处的 `uint16_t`。**[社区一手]**

### 2.2 出怪分两次抽随机，只有一次入档

- **波表**（每波有哪些僵尸）在**建局时**抽定：`Board::PickZombieWaves()` → `PickZombieType()` →
  `TodPickFromWeightedArray()` → `Sexy::Rand(aTotalWeight)`（`Lawn_Board.cpp:575-800, 2528`；
  `Sexy.TodLib_TodCommon.cpp`）。抽的结果写进 Board 成员 `mZombiesInWave[aWave][i]`
  （`Lawn_Board.cpp:549-560`），因此**随 Board 整块入档**，读档后不变。**[源码]**
- 与之相邻但**不同**的一条路径：`Board::GetLevelRandSeed()`（`mPlayerInfo->mId + mBoardRandSeed +
  stage*101 + gameMode`）构造**局部** `MTRand aLevelRNG`，用于关卡地物（墓碑、传送门等，
  `Lawn_Board.cpp:798,1095`、`Lawn_Challenge.cpp:2506`）。`mBoardRandSeed` 本身是 Board 成员，
  **入档**；但每个新 Board 的 seed 在生存模式下来自全局 `Rand()`（`Lawn_Board.cpp:57-61`）。**[源码]**
- 单只僵尸的落地细节来自**全局** `Rand()`：
  `AddZombieInRow()` → `bool aVariant = !Rand(5)`、`mZombies.DataArrayAlloc()`；
  `ZombieInitialize()` → `mGroanCounter = RandRangeInt(300,400)`、`PickRandomSpeed()` →
  `mVelX = RandRangeFloat(0.23f, 0.37f)`、动画速率 `RandRangeFloat(12,24)`、`mAnimTime = RandRangeFloat(0,0.99)`。
  （`Lawn_Board.cpp:2674-2700`，`Lawn_Zombie.cpp:120,973-982,1096-1140`）
- 波长上限与下一波阈值同样来自全局 MT：
  `mZombieCountDown = ZOMBIE_COUNTDOWN + Rand(ZOMBIE_COUNTDOWN_RANGE)`，
  `mZombieHealthToNextWave = RandRangeFloat(0.5f,0.65f) * mZombieHealthWaveStart`（`Lawn_Board.cpp:5496-5520`）。
  社区教程给出的区间（2500~3100 随机上限）与此一致。**[源码]+[社区一手]**
- 全局 MT 属于 `SexyAppBase`，其持久化只写**seed 四个字节**（`SexyAppFramework_SexyAppBase.cpp:572,672`），
  不写 MT 表与游标。

### 2.3 框架自带"此处禁止取随机"的先例

`MTAutoDisallowRand`（`SexyAppFramework_MTRand.h:35`）在 `SexyAppBase.cpp:2573,5175` 被使用，
配套 `DBG_ASSERT(gRandAllowed==0)`。**[源码]** 这说明"表现层不得消费玩法随机流"在原版框架里
已是可断言的纪律，本项目可以直接复用这条纪律做守门，而不必新造概念。

## 3. 读档到底保住了什么

### 3.1 存档内容（`Lawn_System_SaveGame.cpp`）

`SaveGameHeader`（magic/version/编译时间 CRC）之后，`SyncBoard()` 依次写：

| 次序 | 内容 | 备注 |
|---|---|---|
| 1 | `SyncBytes(&theBoard->mPaused, sizeof(Board) - offsetof(Board, mPaused))` | Board 从 +0x164 到结尾的**整块原始字节**，含 `mZombiesInWave`(+0x6B4)、`mRowPickingArray`(+0x654)、`mBoardRandSeed`(+0x561C) |
| 2 | 12 个 `SyncDataArray` | zombies / plants / projectiles / coins / lawnmowers / griditems / particleSystems / emitters / particles / reanimations / trails / attachments，每个 = `mFreeListHead` + `mMaxUsedCount` + `mSize` + 块内容 |
| 3 | 逐对象修正数据 | 粒子/动画/拖尾的 definition 转成枚举写入，读回时按枚举重新取定义指针 |
| 4 | 结构体整块 | cursor / cursorPreview / advice / seedBank / challenge / music |
| 5 | 尾部 magic | 校验 |

注意第 1 步与第 2 步的分工：`mPaused` 位于 `mZombies`(+0x90) 等 DataArray **之后**，
所以整块字节**不包含** DataArray 的头字段，头字段由第 2 步显式处理。**[源码]**

### 3.2 读档侧发生的其他事

- `LawnApp::TryLoadGame()`（`LawnApp.cpp:446`）先 `MakeNewBoard()`，即**新建一个 Board**，
  然后 `mBoard->LoadGame()` 往里覆盖。新建 Board 的构造函数会消耗约 800 次全局 `Rand()`
  （`mGridCelLook` 与 `mGridCelOffset` 的 45×6 循环，`Lawn_Board.cpp:75-77`），这些消耗
  **不会被回滚**，因此即使不谈随机源内容，读档本身也让全局流偏离原时间线。**[源码]**
- `FixBoardAfterLoad()` 只重绑 `mApp`/`mBoard`/音乐接口，**不重建**任何派生结构。**[源码]**
- `Board::LoadGame()` 另外做 `LoadBackgroundImages()`、`ClearUpdateBacklog()`、
  `ResetFPSStats()`、`UpdateLayers()`；`ContinueDialog::RestartLoopingSounds()` 重新发雨声与
  僵尸歌曲。**[源码]**

### 3.3 入档 / 不入档对照

| 状态 | 入档 | 读档后等价 |
|---|---|---|
| 植物/僵尸/投射物/金币/推车/格子物品的槽位分配与空闲链表 | 是 | 等价（未来新对象也会拿到与存档时**相同顺序**的槽位） |
| 对象的"栈位"（`Index()`） | 是（对象字节的一部分） | 等价 |
| 波表、当前波、出怪倒计时、血量阈值、行选择平滑数组、`mBoardRandSeed` | 是 | 等价 |
| 动画时钟（进度/速率/循环） | 是（动画对象在 DataArray 内） | 等价 |
| 全局 MT 表与游标、CRT `rand` 状态 | **否** | **不等价** |
| `DataArray::mNextKey`（ID 代次计数器） | **否**（不在同步范围内，新建 Board 时复位为 1001） | **不等价** |
| 音效设备状态、音乐播放位置、`mAppRandSeed` 等 app 级字段 | **否** | 不等价 |

## 4. 「栈位刷新」应当怎样表述

把上面合起来，可以给出比民间说法更精确的版本：

1. **已存在对象的栈位在存档/读档后保持不变。** 因为栈位是对象字节里的一个字段，随
   `SyncDataArray` 的块内容一起往返。**[源码]**
2. **未来新对象的槽位复用顺序也保持不变**，因为 `mFreeListHead` 与空闲项的链接（写在 `mID` 里）
   同样入档。**[源码]**
3. **读档后行为仍会与原时间线分叉**，原因是两个**没入档**的东西：
   - 全局 MT：出怪行、变体、速度、动画速率、波长上限、下一波血量阈值都会取到不同的值；
   - ID 代次：见 §5。
4. 所以"读档刷新栈位"这个说法**指向的现象是真的，机制描述是错的**。真正的机制是
   "读档保留阵型但重置随机流与代次"。**[推断]**（第 3 条的两个分项中，全局 MT 已由源码直接支持；
   代次项需要 §5 的探针确认其可观测后果。）

## 5. ID 代次（key）重发：一个尚未被评估的等价性缺口

`DataArray` 的 ID 是 `(mNextKey++ << 16) | index`（`Sexy.TodLib_DataArray.h`），
`DataArrayTryToGet()` 比较完整 32 位。而存档只同步 `mFreeListHead`/`mMaxUsedCount`/`mSize`/块内容，
**不同步 `mNextKey`**；新建 Board 会把 `mNextKey` 复位为 1001。于是：

- 档内对象保留着上一场会话分配到的 key（例如 1001..3000）；
- 读档后新分配的对象从 1001 重新开始发 key；
- 档内还存着一批**引用型 ID 字段**：`Plant::mTargetZombieID`、`Zombie::mTargetPlantID`、
  `Zombie::mRelatedZombieID`、`Zombie::mAttachmentID`、各类 `mBodyReanimID` 等
  （`Lawn_Plant.h:165-181`、`Lawn_Zombie.h:142-163`、`Lawn_Projectile.h:49-52`、`Lawn_GridItem.h:40-41`）。

两种后果要分开看：

- **fail-safe 方向**：旧 ID 的 key 与重发后的 key 不同 → `DataArrayTryToGet` 返回 `nullptr`
  → 目标"看起来消失了"。这不会串到别的对象，但会改变行为（例如植物放弃目标）。
- **aliasing 方向**：如果档内引用的 ID 恰好等于重发后某个新对象的 ID（同 key 同 index），
  引用会**指向一个无关的新对象**。这是典型的 ABA 问题。

本项标 **[推断]**：机制由源码直接给出，但"是否在真实对局中产生可观测行为差异"尚无实测。
`docs/determinism-reanimation.md` 已记录过动画**句柄代次**需要归一化，属于同一族问题的既有证据。

## 7. 研究侧：这件事的学术落点在哪

1. **确定性/回放本身主要是工程实践而非学术课题**：lockstep 与状态哈希、rollback netcode、
   确定性仿真测试（FoundationDB/Antithesis 式）都没有形成可直接引用的"PvZ 判定标准"。
   因此本项目的契约必须自己提出并自己验证，不能指望引用外部权威。**[推断]**
2. **真正有学术对应的是"agent 会不会利用规格漏洞"**，这属于 reward hacking / specification gaming：
   - Skalse et al. 2022, *Defining and Characterizing Reward Hacking*（OpenAlex 元数据已核）。**[文献]**
   - Nishimura-Gasparian, McCarthy, Lindner 2026, *Towards Understanding Specification Gaming
     in Reasoning Models*, arXiv:2605.02269——8 个任务中所有被测模型都有非可忽略的投机率，
     且 RL 推理训练**提高**投机率。**[文献]**
   - Caugatan & Zhao 2026, *Reward Hacking in Language Model Agents: Revisiting AI Safety Gridworlds*,
     arXiv:2606.15385——模型零样本即可"观测奖励高但隐藏目标不达标"。**[文献]**
   - DeltaML-Bench 2026, arXiv:2608.19653——报告某配置下 specification gaming 率达 47.9%。**[文献]**
   （以上经 Semantic Scholar / OpenAlex 元数据核实标题、年份与摘要，未通读全文。）
3. **结论**：对一个 LLM 评测来说，"读档/接管/回放文件是不是可被利用"**不是可以留给运气的问题**，
   而是评测设计的一部分。文献给出的稳定结论是：仅靠提示与测试期缓解**降低但不消除**投机率。

## 8. 建议的决策（待拍板）

- **D1 采用 A/B/C 三层合同。** 判分只看 A 层；B 层作为"输入一致性"断言（tick、调用身份、
  RNG 消费次数）；C 层只记录不判等。三层各自的字段清单直接沿用本文 §1 与
  `docs/动画耦合与可重复性取证.md` §6。
- **D2 允许接管式回放器存在，但不能作为 A 层证据来源。** 一旦改动 RNG 分流或把
  `ShouldTriggerTimedEvent` 改成 tick 事件表，必须标注 `original_engine_bitwise_unmodified=false`，
  并且只能用于"阵型级"评测，不能用于原版确定性声明。
- **D3 把"读档"当成一个要**被测试**的操作，而不是一个便利功能。** 对同一存档做 K 次读档，
  在指定 tick 上比对 A 层：预期全等；若不相等，说明 A 层里混入了非入档状态。这一步能直接把
  §3.3 的表格从"读源码得到"升级为"实测得到"。
- **D4 把 exploit 面显式红队并记录。** 至少覆盖：读档/接管接口、暂停与倍速、存档槽位、
  回放文件、外部内存写、时间回拨。**使用这些接口不应当被隐藏成失败，而应当被记为一次带标签的事件**——
  否则我们既得不到干净的评测数字，也看不到 agent 到底学到了什么。

|---|---|---|---|
| P1 | A 层是否真的被存档完整保留 | 同一存档读档 K=5 次，在固定 tick 比对 A 层 | 全等；若不等，定位到具体字段 |
| P2 | 量化"读档改变运阵" | 同一存档：一路继续跑 vs 读档后继续跑，各 1000 tick，比 A 层 | 预期不等（行/速度/阈值漂移），得到漂移量级 |
| P3 | 证明全局 MT 不入档 | 读档后立刻 dump MT 表与游标，与原时间线对应 tick 比对 | 不等价 |
| P4 | 证明 key 重发 | 读档后立刻新建一个对象，检查其 ID 是否与档内某对象 ID 相等 | 出现相等即确认 ABA 面存在 |
| P5 | 栈位稳定性 | 读档前后 dump 所有对象的 `Index()` | 一致 |

P1/P5 若成立，就可以把"读档等价"的表述收敛为：**A 层等价、B 层不等价、C 层自由**。
这正好是本文三层合同的实测背书。
