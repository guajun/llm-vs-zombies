# 同源分支自检流程与抽样策略

日期：2026-09-22。对应 issue [#36](https://github.com/guajun/llm-vs-zombies/issues/36)（[N8] 同源分支自检流程与抽样策略），Epic [#39](https://github.com/guajun/llm-vs-zombies/issues/39)。实现：`tools/branch_selfcheck.py`；测试：`tests/test_branch_selfcheck.py`。

范围声明：本流程只消费**已封包的树**（`evidence_tree.package_tree` 的产物），对比对象是同一棵树内的记录与重新执行结果。R0–R3 按[分支数据合同与实施计划](分支数据合同与实施计划.md) §3.3 的阶梯定义；R4、"真实游戏运行"与任何"原版确定性"声明都不在本流程内，报告中逐条标注。本文不修改任何既有实验结论，也不提升任何已声明能力。

## 0. 摘要

- 一条命令对一棵树抽检：抽到的每个节点，用**同一棵树根**、**同一条记录动作序列**跑两遍，逐帧比较，产出报告。
- 抽样的必选集合是**树根 + 每个分支的起点节点**，其余名额按树索引均匀铺开；默认上限 4 个节点，`all` 为全树。
- 阶梯逐档评估：R0 恢复恒等、R1 恢复后不推进、R2 推进 1 tick、R3 推进 N tick；**任何一档失败即短路**，后档记为 `not_reached`，前档结论与全部原始证据保留。
- 报告绑定 `tree_id`、`branch_id`、节点 `trajectory_id` 与父链 `chain_sha256`，并给出首个分叉位置（节点、档位、帧序号、tick、JSON Pointer、两侧摘要）。
- 工具本身**不启动游戏**：真实运行由 `--executor` 指向的执行器负责，其前置条件见 §5。

## 1. 流程

### 1.1 输入与命令

```powershell
$env:PYTHONPATH = 'src'
python tools/branch_selfcheck.py <树目录> <新输出目录> --executor <module:function> --sample-limit all
```

1. 读入并**整树重算**（`validate_tree`）：树身份、每条父链、分支作用域、每个节点包的证据校验；任一项不通过就直接拒绝，不产生报告。
2. 按 §3 的策略选出抽样节点，并给出覆盖率。
3. 对每个抽样节点连续调用执行器两次（`run-a`、`run-b`），每次得到一份逐 tick 帧序列。
4. 逐帧比较：先比帧序与 tick，再比规范化审计状态；首个不一致处即"分叉位置"。
5. 按 §2 的阶梯给每档结论，写入 `<输出目录>/selfcheck-report.json`。

### 1.2 执行器契约

执行器由 `--executor module:function`（或 `path/to/executor.py:function`）指定，签名为 `executor(sample, directory) -> dict`：

- `sample`：本次抽样节点，字段为 `key`、`path`、`branch_id`、`trunk`、`tree_id`、`trajectory_id`、`chain_sha256`、`parent_key`、`parent_trajectory_id`、`fork`（离开父节点的边界坐标 `{epoch,tick,revision}`，树根为 `null`）、`end`（该节点最后已验证边界）、`root_identity`（游戏/资源摘要、初始化配方、可选镜像摘要）、`trajectory`（节点包目录）、`steps`（该节点记录的全部请求）；`sample.binding()` 给出报告用的身份绑定，`sample.edge_ticks` 是该节点自己的边跨过的 tick 数。
- `directory`：本次运行独占的新目录；执行器把自己的原始证据（会话日志、原生审计等）写在这里。
- 返回值（运行记录）：

| 键 | 要求 |
|---|---|
| `mode` | 非空字符串，说明这次运行是哪种执行方式 |
| `real_game` | 布尔，声明本次是否真的启动了游戏进程 |
| `frames` | 逐 tick 帧序列，见下 |
| `restore` | 可选；恢复证据。**可直接放 `tools/process_snapshot.py` 的 `verify_r0` 返回值**：工具读取 `attempted`、`equal`（缺省回退到 `r0`）与可选 `image_sha256` |
| `identity` | 可选；`{game, artifacts}`。给出时必须等于树根身份，否则整次抽检被拒（不同根不能互比，合同 P3） |
| `root_image_sha256` | 可选；本次恢复所用的根镜像摘要，与 `restore.image_sha256` 等价 |
| `note` | 可选；自由文本，原样保留 |

`frames` 是逐 tick 的**边界状态**列表，每项至少含 `tick`（非负整数）与 `state`（对象，规范化审计状态）：

1. 第一帧必须是 tick 0，即"恢复完成、尚未推进"的边界；
2. 之后每推进一个 tick 追加一帧，tick 非递减；
3. 末帧必须到达 `sample.end["tick"]`，否则该次抽检被拒绝。

比较口径：帧序、tick 与规范化状态；`epoch` / `revision` 由执行器映射，不参与比较（与 `engine_replay` 的 epoch 映射一致）。

## 2. R0–R3 与合同 §3.3 的对应

| 档 | 本合同 §3.3 | 本流程的做法 | 通过判据 | 失败指向 |
|---|---|---|---|---|
| R0 | 恢复后立即重抓，逐字节等于原镜像 | 两次运行的 `restore` 证据 | 两次运行都 `attempted` 且 `equal`；根身份有镜像摘要时，运行摘要必须相同 | 恢复不是恒等变换 |
| R1 | 恢复后不推进，审计状态等于连续运行同刻 | 两侧 tick 0 帧 | `run-a` vs `run-b`，且各自等于**封包的** tick 0 边界 | 抓取 / 恢复范围 |
| R2 | 恢复后推进 1 tick | 两侧 tick 1 帧 | 同 R1，比较对象为 tick 1 | 环境差异首次被读取 |
| R3 | 恢复后推进 N tick | 两侧 tick ≥ 1 的全部帧 | 同 R1，逐帧比到该节点记录的末边界；首个不一致处给出帧序号与 JSON Pointer | 慢速耦合 |
| R4 | 改恢复间隔、主机负载、并行度后仍等价 | **未做** | — | 时间与共享资源（N6 / N10） |

补充说明：

- **R0 不适用时不冒充通过**：从起点重算（合同 §3.1 的 c 路径）没有恢复步骤，R0 记为 `not_applicable`，报告在 `verdict.notes` 里写明。
- **sealed 参照的语义**：R1–R3 的第三条比较对象是同节点自己的封包记录。它与两次新运行同为"同根 + 同动作序列"，所以这是 P1 的第三个样本，而不是 P2：分支节点依旧是反事实的，不存在"原版会怎么走"的对照（合同 §1.1）。用 `--reference none` 可只保留两次新运行之间的比较，报告会标注只检查了 P1。
- **fork 诊断（非阶梯档）**：对非根节点额外比较"离开父节点的那一帧"与封包的父节点同边界帧（版本精确匹配优先，退化到同 tick 并在报告里标注 `match`）。它能区分"前缀没复现"与"分支动作之后才分叉"。
- **短路保留**：某一档失败后，后档记为 `not_reached` 并带 `blocked_by`；失败档保留完整比较记录与两侧状态摘要，前档的 `passed` 不会被覆盖。

## 3. 抽样策略

### 3.1 选点规则

| 规则 | 内容 |
|---|---|
| 必选 | 树根节点；每个分支的起点节点（父节点分支 id 与本节点不同的节点） |
| 可选 | 其余名额按树索引均匀铺开（`round(i·(n-1)/(k-1))`，确定性、可复现），因此同一棵树同一 `--sample-limit` 永远抽到同一批节点 |
| 上限 | `--sample-limit`（默认 4）或 `all`；上限小于必选集合时**直接报错**，不静默丢分支 |
| 覆盖 | `--sample-nodes root,A` 显式指定节点，仅用于定位问题；报告照实记录覆盖率 |

### 3.2 覆盖率口径

报告 `sampling` 同时给出：节点覆盖率（`nodes_sampled / nodes_total`）、分支覆盖率（至少抽到一个节点的分支数 / 分支总数）、边 tick 覆盖率（抽样节点**自己的边**跨过的 tick 数 / 全树各节点边 tick 之和）。共享前缀只按每个抽样节点各记一次，口径写在 `sampling.scope` 里。

建议：日常抽样用默认上限即可；**封包发布前用 `--sample-limit all`**，或至少保证分支覆盖率 1.0。

### 3.3 失败处理

1. 单次抽检内：一档失败即短路该节点，后档不评估（§2）。
2. 多次抽检间：默认继续跑完选中的其余节点，覆盖率数字保持完整；`--stop-on-failure` 可改为首个失败即停，未跑的节点记为 `not_run`。
3. 证据不可覆盖：输出目录必须不存在，工具不会改写已有的报告与运行记录；重跑请换新目录。
4. 执行器违约（缺帧、未到末边界、身份不一致）或抛错时，工具立即中止：已写入的运行目录与执行器原始证据保留，本次不产出报告，错误信息走标准错误。
5. 退出码：0 = `passed`，1 = `failed` 或被拒绝（树校验失败、执行器违约等），2 = 参数错误。
6. 升级路径：R0/R1 失败先修 a2 恢复路径（N5），R2 失败按 §3.4 残余耦合清单逐条排查（N6），只有 R3 失败才怀疑慢速耦合；任何一个失败都不得把该树当作已通过抽检的训练数据源，也不得改写成"部分通过"。

## 4. 报告格式

`selfcheck-report.json` 的 `schema` 为 `lvz.branch-selfcheck.v1`，`report_id` 为去掉该键后的规范化 JSON 的 SHA-256（`sort_keys` 紧凑编码），便于引用整份报告。

| 键 | 内容 |
|---|---|
| `scope` / `comparison` | 本报告覆盖范围与比较口径 |
| `executor` | 实际解析到的 `模块:函数` |
| `reference_mode` | `sealed` 或 `none` |
| `tree` | 整树校验摘要：`tree_id`、根键、节点数、分支、主干节点、分叉点 |
| `root_identity` | 根身份：游戏/资源摘要、初始化配方、可选镜像摘要 |
| `run_labels` | 固定为 `["run-a", "run-b"]` |
| `sampling` | 抽样策略与覆盖率（§3.2） |
| `samples[]` | 每个抽样节点：`binding`（`tree_id`、`branch_id`、`trajectory_id`、`chain_sha256`、父节点与边界）、`request`、两侧 `runs`（记录路径与 SHA-256）、`reference`、`rungs`（R0–R3 逐档）、`fork`、`first_divergence`、`evidence` |
| `rungs` | 各档在全样本上的状态计数（`passed` / `failed` / `not_reached` / `not_available` / `not_applicable`） |
| `first_divergence` | 全报告首个分叉：`node`、`rung`、`comparison`（左/右标签、帧序号、tick、JSON Pointer 与两侧值）、`evidence` |
| `limitations` | `real_game_run`、`original_engine_verified`（恒为 `false`）、说明文字与前置清单 |
| `verdict` | `passed` / `failed` / `incomplete`，附 `failed_nodes`、`unevaluated_nodes` 与说明 |

运行证据按 `<输出目录>/runs/<节点>/<run-a|run-b>/` 存放：`record.json` 是归一化运行记录（`frames`、`restore`、`identity` 绑定、`tick_range`），执行器自己的原始文件（会话日志、原生审计）放在同一目录，报告用相对路径 + SHA-256 引用。

失败报告片段（示意）：

```json
{
  "node": "A",
  "rungs": {
    "r1": {"status": "passed", "frames": 1},
    "r2": {"status": "failed", "first_difference": {"reason": "state", "index": 0, "tick": 1,
      "difference": {"path": "/board/hidden", "reason": "value", "expected": 0, "actual": 999}}},
    "r3": {"status": "not_reached", "blocked_by": "r2"}
  },
  "first_divergence": {"node": "A", "rung": "r2", "points_to": "an environment difference is read for the first time"}
}
```

## 5. 前置与未做

本 issue 只交付流程、抽样策略与报告格式；在真实树上运行还需要：

1. a2 外部快照/恢复实现（N5、`tools/process_snapshot.py`）：在暂停边界抓取树根镜像，并把该镜像恢复回目标进程；同一次挂起内的 `verify_r0` 报告可直接作为 R0 证据。
2. 一个 `--executor` 可引用的执行器：启动受控目标（launcher + 固定运行时构建 + 独立用户档）、恢复根镜像、按 `sample.steps` 执行、并给出逐 tick 审计状态。
3. 运行身份与树根身份一致（游戏、资源摘要、运行时构建），否则报告不会把它当作"同根"。
4. R4 需要恢复间隔、主机负载与并行度的变化（N6 / N10）。

明确未做：不启动游戏、不跑长局、不改运行时原生代码、不做 R4、不产生任何"原版确定性"或"完整状态覆盖"声明。合成夹具上跑通的只是流程本身（`tests/test_branch_selfcheck.py`），通过它不等于真实游戏上的同源分叉决定论已成立。
