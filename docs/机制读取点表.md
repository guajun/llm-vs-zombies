## 0. 摘要

**五条硬验收条目的一句话结论**（详细展开见 §2）：

1. **槽位编号（栈位）**：`Board::IteratePlants` / `GetPlantsOnLawn` 严格按 `DataArray` 块索引升序遍历，同格冲突时**小编号先被处理**——同一个"编号"字段在遍历顺序上是**值（进 S）**，在引用解析时是**身份（可归一化）**。
2. **波表与出怪阈值**：`mZombiesInWave`、`mZombieCountDown`、`mZombieCountDownStart`、`mZombieHealthToNextWave/WaveStart` 都在取值的时刻用全局 `Rand` 抽定后写进 `Board`，随 `SyncBoard` 的整块字节**随存档往返**；抽样用的是不入档的全局 MT。
3. **`DataArray::mNextKey` 代次计数器**：新 ID 由 `(mNextKey++ << 16) | slot` 生成，代次决定新对象是否会与档内旧引用撞车；`SaveGame` 的 `SyncDataArray` 不写 `mNextKey`，读档路径复位为 1001——**机制成立、后果待实测**（本条结论必须标 [推断]）。
4. **动画时钟**：`Reanimation::mAnimTime` / `mLastFrameTime` 是玩法时钟而**不是纯表现**——`ShouldTriggerTimedEvent(0.64f)` 直接决定巨人锤击砸掉哪一格植物，属每 tick 读取的进 S 量。
5. **浮点控制字**：x87 CW（目标 `0x027f`）与 MXCSR 控制位（目标 `0x1f80`）参与每一次浮点算术与阈值比较；048 已有实测：冷启动未执行受控更新时就有 7 处字段差异，其中首项就是 x87 `0x007f` 对 `0x027f`。

**枚举规模**：94 条记录 = 19 条深度记录（对应 5 个主题）+ 75 条低分辨率枚举记录，覆盖 13 个子系统。

## 1. 判据、单位与词表

### 1.1 进 S 的判据（合同 §2.1）

一个量进 S 当且仅当它参与**比较 / 选择**、**算术**、**随机消费**三者之一。只用于寻址、查找、显示、日志的量不进 S。

### 1.2 分析单位是 (字段, 读取点)（合同 §2.2）

同一字段在不同读取点可以扮演不同角色：对象指针/句柄在查找时是**身份**（数值可归一化），被当作随机种子时是**值**（数值决定结果）。本表因此不给"字段"下结论，只给"读取点"下结论；同名字段出现多行属正常。

### 1.3 三档结论

| 结论 | JSON 值 | 含义 |
|---|---|---|
| 进 S | `enter_s` | 该读取点读到的数值进入转移函数输入集合 |
| 可归一化为身份 | `normalize_as_identity` | 该读取点只关心"是不是同一个对象"，位模式差异可归一化掉 |
| 不进 S | `exclude` | 该读取点只用于寻址 / 显示 / 日志 |

### 1.4 证据等级

| 标记 | 含义 |
|---|---|
| **[源码]** | 候选反编译副本（`work/replay-research/`，PvZ 1.0.0.1051，固定提交 `8a2d1218`）的具体文件:行号，与既有文档的 [D] 同级：未逐条独立反汇编 |

标题级硬约束：第 3 条（`mNextKey` 后果）在第 1.4 节的口径下只能是 **[推断]**；本表未把它写成既定事实。

### 1.5 记录字段与词表

- **trigger**：`每 tick` / `建局时` / `出怪时` / `特定状态` / `加载时` / `绘制时` / `音效查询时` / `存档时`
- **effect**：`分支` / `算术` / `随机消费` / `无（仅寻址/显示）`
- **status**：`已核（未实测）` = 源码路径已逐行读过；`待核实` = 只有间接或部分路径，需实测或补读

### 1.6 边界

读取点既包括**游戏引擎侧**（反编译副本），也包括**宿主侧**（本仓库 `determinism/`、`src/llm_vs_zombies/`、`runtime/`）。理由：本项目运行在 AvZ 接管 + 受控宿主下，浮点控制字、绘制调度、音效分配模式本身就是进入转移函数的输入（048 / 036 / 010 已有实测）。社区一手读取点（`avz/framework/inc/avz_pvz_struct.h`）同样计入边界，因为脚本在该边界内做决策。

### D3 `DataArray::mNextKey` 代次计数器：机制成立、后果待实测

**结论（一句话）**：`mNextKey` 是"已发出 ID 的代次"，它决定读档后新 ID 是否会与档内旧引用撞车；机制由源码给出，**后果未实测，属 [推断]**。

两个方向的后果（均为 **[推断]**，未实测）：

- **fail-safe 方向**：旧 ID 的 key 与重发 key 不同 → `DataArrayTryToGet` 返回 `nullptr` → 目标"看起来消失了"（例如植物放弃目标）；
- **aliasing 方向**：档内引用的 ID 恰好等于重发后某个新对象的 ID（同 key 同 slot）→ 引用指向无关的新对象（典型 ABA）。

引用型字段清单（[源码]，行号来自既有调研）：`Plant::mTargetZombieID`（`Lawn_Plant.h:165-181`）、`Zombie::mTargetPlantID` / `mRelatedZombieID` / `mAttachmentID` / `mBodyReanimID`（`Lawn_Zombie.h:142-163`）、`Projectile`（`Lawn_Projectile.h:49-52`）、`GridItem`（`Lawn_GridItem.h:40-41`）。

**待核实**：合同 §7.2 的 P4（读档后立刻新建对象，比对其 ID 是否等于档内某对象）是唯一能把本条从 [推断] 升到 [实测] 的低成本实验；长局是否真的回绕（D3-2）同样未观测。
