# 原版确定性重放器提案

日期：2026-09-18。状态：**技术提案，未启动游戏、未注入、未验证确定性**。本文所称“原版”是继续使用已锁定的 PvZ 引擎和运算规则；进程内增加控制、记录及校验模块，不以重写战斗模拟器代替游戏。

## 1. 推荐结论

采用 **初始状态 + 按帧语义动作 + RNG/时间控制 + 每帧校验**，由原版引擎重新运算。先保证从起点顺序重放，再实现中途检查点和跳转。现有 HTML 状态流播放器继续承担快速复盘，不作为可接管游戏的确定性证明。

建议新增一个独立于策略的原生模块 `determinism-core`，首版与 AvZ、logger、LLM 常驻适配器编译进**同一个 32 位 runtime DLL**。模块可独立设计，但不应一开始就另注入第二份拥有 AvZ 主循环的 DLL。

```text
Python 持久 REPL / LLM              离线动作重放器
            └────── 同一命令协议 ──────┘
                           ↓
                 IPC 队列 / 帧号校验
                           ↓
   runtime DLL：唯一游戏线程执行器 → AvZ 动作与观察
                  ↕
   determinism-core：帧边界、RNG、状态摘要、恢复
                  ↓
    动作与事件日志 + 校验流 + 可选快照 + 视频
```

LLM 不生成每步都要编译的 C++。它向常驻程序发数据命令；回放器读取同一数据命令。编译只发生在增加底层能力时，详见 [LLM 交互控制设计](LLM交互控制设计.md)。

## 2. 已有证据与待验证边界

**本项目源码可证明：**

- AvZ 固定提交 `c42676c269b5b482a1eb9203a5b979e9d8a2a5c7` 可复用实体访问、种植/铲除、波次观察和存读档调用。

- `SaveGame` 对某些受控小丑写入修正；`LoadGame` 重建 Board、处理音频引用、继续局面及更新 AvZ 刷新时间。因此它们不是无副作用的完整进程快照。[存读档实现](https://github.com/vector-wlc/AsmVsZombies/blob/c42676c269b5b482a1eb9203a5b979e9d8a2a5c7/src/avz_asm.cpp)
- 现有 logger 只采部分状态，`phase=avz_callback`；首次观测不是精确出生事件，也未捕获全部手动输入。其 `compare` 只证明已记录字段相同。

## 3. 必须建立的确定性契约

### 帧、暂停和输入

定义边界 `B(t)` 为执行本帧动作之前的稳定状态；按 `ordinal` 顺序执行动作，运行一次已经验证的原版模拟步及对象清理，得到 `E(t)`，随后才递增控制器 tick。明确把游戏自身时钟作为独立字段记录，不能把一次外层回调当作一个模拟步。

首版固定一种正常推进路径，暂不开放 AvZ 跳帧加速。调查调用链后，在同一控制模块中提供可靠的 `pre_step/post_step`；当前 `AOnAfterTick` 不够。跨菜单、选卡和两旗结束的状态转换另记 segment 与 epoch。

暂停等待 LLM 时继续泵 IPC/窗口消息，但不得让这些工作改变受控模拟状态。验证暂停期间移动光标、窗口失焦、等待 60 秒、不同渲染次数是否消耗共享 RNG。若会影响战斗，先固定其调用序列或收紧暂停路径；未经证实不要简单拆分随机流，因为拆分本身会改变原版结果。

真实鼠标键盘、自动收阳光、修补器、其他脚本必须进入统一执行入口，或在严格实验中禁用。混入未记录动作应使记录失去“可确定性重放”标记。

### RNG、时间和浮点环境

逆向审计所有影响模拟的随机入口：全局/局部 RNG、CRT 随机、生成函数及重新播种。记录完整状态、实例标识与每帧调用计数；诊断模式记录调用点的模块 RVA、参数、返回值和顺序。跨进程使用模块标识/RVA，不能记录裸返回地址作为稳定身份。

先查 `GetTickCount/timeGetTime/QPC/time/_time64` 等是否真正影响玩法。只对确认的游戏时间源提供固定值或按模拟 tick 推进；IPC 超时、日志写盘仍用真实时间。锁定 x87/SSE 浮点控制状态与运行版本，检查音频/加载线程是否写入影响模拟的数据。初始种子应在相应初始化之前设置；中途恢复需完整 RNG 状态，不能重设初始种子了事。

“随机返回值磁带”只作为诊断和单轨迹重放后备：每条必须匹配入口、调用点、参数和次序；不匹配立即停止，不能继续吐出随机值来掩盖分叉。若替换返回值，还要处理生成器状态的推进与恢复，否则不能从回放中途接管。优先让原 RNG 自然产生相同结果，以免改变正常机制。

### 初始状态与中途快照

第一阶段把重启进程后执行固定初始化流程作为权威恢复方式：锁定 exe/数据包/DLL、隔离实验用户档、加载同一基准局面、固定 RNG 与已确认全局状态，在 `B(0)` 校验后开始。若从菜单初始化更易复现，就先录菜单到基准局面的引导序列。

后续尝试 `.dat + sidecar`。候选原版存档包含 Board、多类对象及部分效果，但尚不能证明包含全局 RNG、线程状态或 AvZ 状态。[候选序列化](https://github.com/ruslan831/PlantsVsZombies-decompilation/blob/8a2d121899ba5cb4df644cd7d2e4c1aaf88dd238/Lawn/System/SaveGame.cpp)

sidecar 审计范围包括：所有 RNG 与时钟；植物/僵尸/弹丸/阳光/推车/场地状态；影响命中时机的动画；对象池空闲表、代次与关联 ID；波表和刷新阈值；卡片、光标；必要的 App/Challenge 状态；控制器 epoch、待执行命令和动作偏移。不要把带指针的原始内存跨进程直接拷回。加载过程自身可能消耗随机数，最终应在禁止更新的边界恢复 RNG 并重新校验。

首版禁止需要序列化任意 C++ lambda/协程的自动策略，待执行操作采用显式数据队列；离线回放关闭 LLM 与原策略。检查点只在清理完成、没有执行中命令时生成。若保存会改变局面，检查点必须修复为可验证的无扰动捕获，或只提供从起点重算，不能默默接受不同轨迹。

## 4. 模块与记录格式

建议职责：`version_probe` 核对模块及代码签名；`tick_driver` 管理帧与暂停；`rng_audit` 管理随机状态；`state_codec` 计算/恢复状态；`command_executor` 供 REPL 和 replay 共用；`replay_player` 调度录制动作。

AvZ 本身通过虚表入口安装主循环，并在卸载时恢复固定原入口。两个独立 runtime 互相覆盖会破坏链路。[hook 实现](https://github.com/vector-wlc/AsmVsZombies/blob/c42676c269b5b482a1eb9203a5b979e9d8a2a5c7/src/avz_hook.cpp)

因此首版采用一个安装器/一个 hook 所有者；新增 RNG 或生成函数观测由它统一登记。若将来拆出 DLL，使用显式 C ABI 注册回调与生命周期管理，禁止第二份 AvZ 再占主循环。安装前验证原字节，卸载前核对当前所有权；安装不完整则撤回本模块改动并拒绝开始实验。不要把任意地址写内存暴露给 LLM。

建议扩充实验目录，但保留现有 `events.jsonl` 兼容：

| 文件 | 必须表达的内容 |
|---|---|
| `replay/manifest.json` | 版本、初始化来源、能力、状态模式版本、控制规则、终点 |
| `replay/commands.jsonl` | `epoch, segment, tick, revision, phase, ordinal, request_id, op, args, result`；区分请求边界和实际执行边界 |
| `replay/checksums.bin` | 每帧分模块摘要：RNG、波次、对象、卡片、控制器 |
| `replay/rng.trace` | 可选诊断调用记录，不默认交给模型 |
| `checkpoints/` | 状态数据、sidecar、所属边界及恢复验证结果 |
| `replay/desync.json` | 首次差异、相关字段、最近动作与 RNG 上下文 |

语义动作应包括失败尝试、同帧顺序、收阳光/选卡等全部外部干预；只保存成功种植会漏掉潜在副作用。原始输入适合人工录制，另存逻辑坐标、按下/释放、焦点及接收相位，之后走同一执行器。只记录高层策略意图如“自动补南瓜”不够，应展开为实际发生的动作。

浮点按位记录，不用四舍五入后的 JSON 数值作唯一校验；规范化对象按稳定 ID 排序，排除地址和无关日志计数，保留影响模拟的池顺序与状态。发现差异立即停在第一帧并展开字段；不得用下一检查点自动纠正后仍声称确定性。校验始终标明覆盖字段，有限测试不等于数学上的全状态证明。

## 5. 开发顺序与验收

| 阶段 | 最小工作与通过条件 |
|---|---|
| P0：定位 | 确认实际加载模块、帧调用链、RNG/时间入口及原生 demo 是否存在；形成有证据的版本适配表，不先猜地址。 |
| P1：共同动作路径 | 无 LLM，固定 1000 tick 的种植/铲除/失败动作脚本；恰好推进指定步数，同帧顺序无歧义，暂停可接收命令。 |
| P2：从头重放 | 固定起点与动作，至少 10 次冷启动跑完一个两旗周期；每帧审计字段、RNG、波表、出生事件和动作结果完全相同。出现任何差异即失败。 |
| P3：扰动实验 | 分别改变暂停时长、窗口焦点、渲染频率、日志/视频开关；再测试加速路径。各条件重放一致才开放相应能力。 |
| P4：检查点 | 在出怪、冰冻、小丑开盒、巨人投掷、模仿者变身等时点保存；同进程和冷启动恢复后均与连续运行逐帧相同。需覆盖跨选卡分段。 |
| P5：接 LLM | REPL 录制一次，关闭模型后原版重放；再接视频导出与分支管理。断线保持暂停，重复 request_id 不重复执行。 |

P2 无法通过时先缩短场景、开启 RNG 调用追踪及全量差异窗口，定位首处分叉；不要立刻重写引擎。P4 失败可交付**从起点重算后跳到目标帧**，代价只是等待。若最终不能保持模拟确定性，交付视频 + 状态流复盘 + 明确标注的 AvZ 存档播放；这能保存实验事实，但不能宣称可恢复接管或严格输入重放。

## 6. 与 benchmark 的区别

固定轨迹 replay 要求“同初态、同动作、同外部条件 → 相同后续状态”。回放不会重新请求 LLM。

不同策略 benchmark 只共享初态/种子集，操作改变后，随机调用顺序、自然刷怪时机及未来行路可能不同；这不构成 replay desync。若要求策略之间每波行路也一致，应另设固定出怪场景或独立外部事件流，说明改变了随机耦合规则，不能把某次游戏的整条 RNG 磁带直接用于所有策略。

当前最重要的未决问题是：本版本实际 RNG 与原生 demo 路径、真正帧边界、暂停/渲染对 RNG 的影响，以及 `.dat` 缺失状态。**下一步先做 P0/P1 的小型验证工具，暂不实现完整快照系统。**
