## 0. 结论（先看这个）

1. **本次分叉没有落到板上**：B 的第 13 个决策（额外一株 col 6 小喷菇）被引擎拒绝，错误码 `card_not_usable`（`executed_ticks=0`）。B 的植物池与 A 逐帧相同（含 `used`/`count`/`next_key`），B 侧从未出现第二株小喷菇。
2. **首个状态分歧：不存在。** 两个 run 的审计状态流 4000 帧逐帧相同（native 分区摘要 + 逐字段精确比对都为 0 处不同）。因此**首个行为分歧也不存在**。
3. **后摇结束后的移速**：A = `0x3e915324`（0.2838374376296997），B = `0x3e915324`（0.2838374376296997），**逐位相同**。这个"相同"是分叉未生效的结果，**不能**当作"分叉不改变巨人恢复行走速度"的证据。
4. 两个 run 之间唯一可观测的差别是**审计流序号**：第 802 帧（`tick 401 pre_step`）A `seq=869` vs B `seq=872`——被拒绝的请求多消耗了 3 个 recorder 序号。这属于信封层，不是状态。
5. 顺带拿到一个**机制级实测**：tick 609 `post_step` 的新 `mVelX` 可以用 tick 608 `post_step` 记录的全局 MT 状态**原值复算出来**——该帧第一次 `NextNoAssert()` 抽取经 `RandRangeFloat(0.23f, 0.37f)` 恰好给出 `0x3e915324`。D6-1 的"重采样点 = `+0x34`、取全局 MT、值域 0.23~0.37"由 [源码] 升级为**本 run 实测**。

## 1. 口径（用户亲自纠正过的版本）

* 场景：巨人向前走 → 进入锤子索敌范围 → 种小喷菇 → 让它砸下 → 继续走。
* **A 与 B 都有小喷菇**：A 是 col 7 那株诱饵；B 额外在 col 6 多一株。
* 观测量是**各自的小喷菇被砸完之后、巨人恢复行走时的移速**（`Zombie +0x34` 的 IEEE-754 原始位；原始位相等才算相等，不用四舍五入的小数）。
* **根到放下小喷菇之间的移速不做比较**。理由：那一段速度由出怪与 `LoadReanim` 自己的抽样/时序决定（`Zombie::ZombieInitialize` 的 `PickRandomSpeed`（`Lawn_Zombie.cpp:166`）随后又被 `LoadReanim` 里的 `StartWalkAnim(0)`（`986`）覆盖，见 D6-4），它是**场景搭建过程**，不是分叉落点；把它纳入比较，等于把"场景初始化差异"当成"分叉效应"。本报告只在 `B(0)` 记录该值作为时间线起点，不参与 A/B 比较。

### 7.1 用审计记录的 MT 状态复算 tick 609 的重采样值

审计每帧都记录全局 MT 的 `words[624]` 与 `cursor`（`sexy_mt19937_31`），因此重采样点可以**原值复算**（引擎实现取自 `work/replay-research/SexyAppFramework_MTRand.cpp` 与 `Sexy.TodLib_TodCommon.cpp`）：

* 快照：tick 608 `post_step`，`cursor=140`（`words` 在 608→609 之间没有重排，两次快照逐字相同）。
* 608→609 之间第一次抽取（`draw_index=0`）：`NextNoAssert()` = `825821557`（0x31390975）。
* 公式：`mVelX = RandRangeFloat(0.23f, 0.37f) = Rand(0.37f - 0.23f) + 0.23f`，其中 `Rand(float r) = (float)((double)w / (double)0x7FFFFFFF * r)`；按 float32 逐步取整后 `round32(round32(825821557/0x7FFFFFFF * 0.14f) + 0.23f)` = **0.2838374376296997 = `0x3e915324`**，与审计里巨人 `+0x34` 的新值**逐位相同**。
* 同一个快照的 512 次抽取中，只有 `draw_index=0` 能给出该位模式（`matches=[0]`）。

这条复算同时说明三件事：该重采样确实**消费全局 MT**（所以分叉一旦改变 MT 消费时序或次数，取值就会变）、`+0x34` 的原始位约定与 `docs/机制读取点表.json` 一致、以及本工具对审计流的重建是保真的。

## 8. 取不到的数据（如实列出）

1. **D6-5 的走路动画变体**（`anim_walk` vs `anim_walk2`）：审计的 `reanimations` 状态不含 definition/动画名，只有 `frame_count`、`loop_type`、`loop_count`、`anim_time(_bits)`、`anim_rate_bits` 等；本 run 里砸击前后 walk 段的 `frame_count` 都是 49，无法区分变体。**没有替代观测**。
2. **单次 MT 抽取的归属**：`cursor` 只给出每帧的总消费次数（tick 608→609 为 140→208），同一 tick 内其它实体的消费无法逐次归因；能确证的只有"该帧第 1 次抽取就是重采样值"。
3. **子 tick 顺序**：审计只有 `pre_step`/`post_step` 两个边界，`mLoopCount` 翻转与 `StartWalkAnim` 是否落在同一次引擎更新内，从快照上不可判（D6-3 已标 [推断]）。
4. **分叉效应本身**：因为分叉被拒（§5），"A/B 恢复行走速度是否不同"这个问题**本次没有任何数据**；B 侧的"第二株小喷菇"在任何帧、任何分区摘要里都不存在。B 侧该请求的响应里 `card_not_usable` 是引擎给出的原因，**其内部判定细节不在审计里**。
5. 巨人投掷（D6-4 的 2202）与泳池分支在本 run 未触发，因此没有它们的取值。
6. **`x` 位移不是 `mVelX` 的固定倍数**：本 run 里同一段 `mVelX` 下的每 tick 位移在 0.0931（tick 400–401）、0.2371（tick 609–620）、0.1310（tick 1000–1500）之间变化，说明除 `+0x34` 之外还有别的位移尺度在起作用（减速/动画相关状态不在本报告口径内，未定位）。因此本报告**只用 `+0x34` 的原始位做速度比较**，不拿 x 位移当代理量。
7. **没有降采样、也没有缺字段**：两个 run 的 `state-deltas` 都是 1 个首态 + 3999 条 patch（tick 0 的 pre 边界 + 每个 tick 的 pre/post 各一条）；巨人槽 11 存在的 **3998** 帧里，`+0x34` 每帧都有记录（A、B 都是 3998/3998，0 帧缺字段）。所以本报告里的"每 tick"就是审计粒度本身，不存在抽样间隔。
