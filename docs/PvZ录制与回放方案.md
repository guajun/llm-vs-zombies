# PvZ + AvZ：完整对局录制、日志与可重复回放

核查日期：2026-09-18。源码基准：`vector-wlc/AsmVsZombies@c42676c269b5b482a1eb9203a5b979e9d8a2a5c7`。

本文是源码评估与建议设计，尚未连接 PvZ 进程验证性能、随机状态恢复或回放一致性。文中的采样频率是建议配置，不是 AvZ 自带的完整录制服务。

## 1. 建议采用的组合

对 LLM 逐帧操作，建议同时记录三条数据流：

1. **动作与决策日志**：精确到游戏帧，保存实际执行顺序、参数、成功或失败结果，以及 LLM 当时收到的观察和返回的动作。
2. **游戏事件与状态日志**：记录实体出生、销毁和关键状态变化；周期性保存状态摘要及校验值。
3. **按游戏时间采样的视频**：例如每推进 4 个逻辑帧渲染并取一次画面，直接送给编码器生成 25 fps 视频。

另存初始局面和少量检查点。需要查看每一逻辑帧的错误细节时，再启用短时间、高密度的 AvZ 回放缓存。

视频负责观看，日志负责分析；能否让原版引擎准确重新运行，还需要确定性验证。

## 2. 慢速流式视频如何工作

AvZ 的时间教程把一帧定义为 1cs，即 0.01 游戏秒。游戏逻辑时间与真实墙钟时间应分开。[S1]

推荐流程：

```text
推进游戏逻辑 → 到达采样帧 → 完成该帧渲染 → 复制画面到内存
                                         ↓
                                  有界队列 / 管道
                                         ↓
                                  视频编码器 → 文件
```

假设每 4 个游戏帧采集一张，采集 250 张就代表 10 游戏秒。即使 LLM 思考导致这段操作花了半小时，输出仍可以是 10 秒、25 fps 的视频。编码器可以等待下一帧，不需要在等待期间不断写入重复画面。

实现方式可以是向 FFmpeg 的 `rawvideo` 输入管道写连续像素数据，约定固定宽高、像素格式和输入帧率；也可以直接调用编码库。不要为每张图编码 PNG、创建文件，再重新读取拼视频。FFmpeg 支持原始帧输入和显式帧率；视频时间由帧率或时间戳决定。[S2]

注意：

- 按游戏帧均匀采样，可以使用固定帧率输入；按不规则事件取图，则必须记录真实游戏时间戳，并用可传递时间戳的编码方式。
- “每次 LLM 返回动作后取一张”不是均匀游戏时间采样，直接按固定 fps 拼接会扭曲节奏。
- AvZ 的 `ASkipTick` 会省略窗口刷新。不能在跳帧时任意截取窗口并认为它是当前帧；必须在采样点暂停推进并确保渲染完成，或接入渲染流程。[S3]
- 推进很慢时可以流式写文件；若同时向网络直播，播放器缓冲和超时是另一层问题。
- 25 fps 视频不保留所有 100 Hz 逻辑帧；精确操作仍由日志记录。若必须观看每个逻辑帧，可按 100 fps 保存，或者导出指定片段的慢放。
- H.264 等视频编码适合观看，但有损画面不宜用于像素级一致性校验。需要像素级校验时另用无损输出。
- 游戏音频不能直接按真实半小时的声卡录音拼到 10 秒视频上；第一版可不录音，后续在正常速度回放导出时录制音频。

这仍有渲染、像素复制和编码成本，但省掉了逐帧图片文件的编码及文件系统开销。实际成本应在目标设备测量。

## 3. 每只僵尸能记录什么

可以记录。AvZ 的 `AZombie` 已提供如下字段访问器：[S4]

| 内容 | 示例访问器 | 说明 |
|---|---|---|
| 身份 | `Id()`、`Index()`、`Rank()` | 数组槽位会复用，不能只用地址或 `Index()` 识别整局实体 |
| 类型、行路 | `Type()`、`Row()` | `Row()` 是从 0 开始的索引；日志需要声明约定 |
| 位置 | `Abscissa()`、`Ordinate()` | 浮点位置，不应仅四舍五入成格子 |
| 速度 | `Speed()` | 是暴露的横向速度字段，不代表所有状态下实际每帧位移 |
| 血量 | `Hp()`、`OneHp()`、`TwoHp()` | 本体及两类饰品血量 |
| 状态 | `State()`、`StateCountdown()` | 可用于追踪举锤等状态及其倒计时 |
| 效果 | `FreezeCountdown()`、`SlowCountdown()`、`FixationCountdown()` | 冰冻、减速、黄油固定 |
| 时间、波次 | `ExistTime()`、`AtWave()` | 波次语义和下标约定需在目标版本验证 |

“随机属性”不是一个单独的万能字段。生成后已经写入实体的随机结果，可以在确认字段语义后记录；尚未发生的随机事件、全局 RNG 状态、未暴露的特殊字段，仍需要额外调查。

**初始位置必须在初始化完成后、第一次更新之前记录。** 如果只在每帧末遍历数组，新出现僵尸可能已经移动过。普通诊断可以记录 `first_observed`；声称准确记录出生状态，则需要合适的生成函数钩子。创建后同帧死亡的实体，也可能被简单的前后数组差分漏掉。

建议事件字段至少包含：

```text
run_id, segment_id, branch_id, tick, phase, sequence
entity_record_id, game_entity_id, event_type, payload
```

`entity_record_id` 由记录器分配；跨读档、跨选卡周期不要假定游戏 ID 永远唯一。实体关联（例如小鬼与巨人）也应记录，并区分直接读取的关系与推断关系。

## 4. Logger 能否直接使用

低频诊断可以用 `ALogger<AFile>`。不过当前源码的文件 logger **每输出一条消息都会调用 `flush()`**；逐帧逐僵尸输出大量文本，可能制造不必要的 I/O 和格式化开销。[S5]

正式录制建议：

1. 游戏线程只读取状态，并复制成不可变记录。
2. 记录进入有界内存队列。
3. 后台写入线程按块写文件；不要让后台线程直接访问可能被回收的游戏对象指针。
4. 调试版用 JSONL；大规模评测可改为带模式版本的二进制记录，并分块压缩。
5. 动作和实体生命周期事件不丢失；队列满时暂停模拟或明确标记本次记录不完整。

可先记录出生/消失/动作等事件，以及每 10～20 游戏帧的状态样本。若目标是查出“一帧之差”，则还应每帧计算状态摘要，或保留关键区间的逐帧状态。

只记录变化不一定总能大幅减小体积：位置每帧都在变。压缩率、字段筛选和采样间隔需要实测。

## 5. 为什么僵尸日志还不是可加载存档

仅有每只僵尸的类型、行路、初始位置、血量，不包含游戏继续模拟所需的全部状态。例如：

- 植物状态、攻击倒计时、弹丸和当前碰撞关系；
- 卡片冷却、阳光对象及其收集状态；
- 冰道、弹坑等场地状态；
- 波次进度、刷新阈值和倒计时；
- RNG 内部状态及后续调用顺序；
- 特殊僵尸状态、对象之间的引用、部分动画状态；
- AvZ 调度队列、脚本变量、自动操作器状态。

这是需要审计的状态类别，不是已验证完整的字段清单。不要把对象原始内存直接写盘后在另一个进程 `memcpy` 回去：其中可能含有地址、引用和与分配器有关的数据。

不同记录目标对应不同技术方案：

| 方案 | 回放机制 | 能否接管继续玩 |
|---|---|---|
| 视频 | 播放像素 | 不能 |
| 实体轨迹查看器 | 依据状态流画出对象 | 不能保证，只重建记录的表现 |
| 初始状态 + 动作流 | 原版引擎重新执行操作 | 在确定性和恢复完整性成立时可以 |
| 检查点 + 状态增量 | 恢复后按协议应用对象变化 | 展示可行；要继续模拟必须有完整模拟状态 |

## 6. 类似 CS2 demo 的可能性

技术上可行，但要明确想要的是“可观看和跳转”还是“精确重新模拟并接管”。CS2 分发的 demo 协议中有 packet、full packet、字符串表、用户命令等消息结构；它不等于只保存鼠标键盘操作。参考的是随游戏分发的协议定义镜像。[S6]

PvZ 没有现成供 AvZ 使用的同类网络状态协议，需要自己定义记录与播放器。

### 路线 A：确定性动作回放

保存初始局面、游戏与框架版本、游戏 RNG 状态、AvZ RNG 状态、实际动作序列及校验值。回放时禁用原策略与 LLM，按原来游戏帧和帧内顺序执行已记录动作。

优点是记录较小、使用原版引擎渲染；难点是 RNG、时间源、加载行为及脚本状态必须可重复。只固定 `aRandom.SetSeed()` 不代表固定 PvZ 自身 RNG。

如果动作由 AvZ 直接调用游戏函数执行，就应记录这些语义动作或等价的底层调用。单独录制操作系统鼠标键盘会漏掉它们。自动收阳光、自动修补等组件的实际动作也要进入日志。

从中途检查点恢复时，保存的是当时完整 RNG 状态，或有能力恢复到对应的随机序列位置；只保存最初的种子通常不够。

### 路线 B：状态流回放

记录关键帧和实体状态差分，让播放器展示录制的结果，减少对未来 RNG 一致性的依赖。可以先做独立查看器，再考虑在原版中创建、更新、销毁对象。

在原版中实现时，要处理对象关联、动画、特殊效果以及禁用原版自主更新，避免同时被播放器和游戏逻辑推进。它的工程量明显大于“给 logger 多加几个字段”。

状态流能展示历史，并不自动意味着可以从任意时刻接管继续游戏。

### 选择建议

先尝试路线 A，并建立分叉检测；若目标版本确定性难以控制，则保留视频与诊断日志，并采用 AvZ 的存档回放作为过渡。只有确实需要随意跳转、查询实体和独立播放器时，再投入完整状态流协议。

记录全局 RNG 的所有返回值也不是对比不同策略的通用解法：相同动作轨迹可能重放成功，换策略后调用次数、顺序或参数变化，就需要调用标识及一致性检查；不能无条件复用同一串返回值。

## 7. AvZ 自带 AReplay 的实际能力

源码中 `_RecordTick()` 会按间隔调用 `AAsm::SaveGame()` 写 `.dat` 文件；`ShowOneTick()` 通过 `AAsm::LoadGame()` 加载对应文件。它另行保存鼠标和部分时钟等附加数据。[S7]

重要限制：

- 默认 `StartRecord()` 每 10 游戏帧保存一次。
- 默认最大保留 2000 个记录，超出后覆盖较老记录。按 100 游戏帧/秒、10 帧一次换算，默认窗口约为 200 游戏秒。
- 录整局时必须按预计时长配置容量，或按周期分段归档。一次无尽并无天然“整局结束”，需要先定义两旗、二十旗等终止条件。
- `_ExitFight()` 会调用 `Stop()`。跨选卡周期要管理分段目录、开始/结束事件和全局时间轴；不能假定一条 StartRecord 会自动覆盖整个多轮无尽。
- 它支持压缩；官方教程明确说存读档 I/O 成本较大，并介绍了 RAM disk 优化。RAM disk 降低 I/O 延迟，不消除序列化和数据体积成本。[S8]
- `SetInterpolate(true)` 会让游戏更新函数补出存档之间的帧，教程警告可能出现数据不一致。精确取证时用 `false`，或者把中间帧明确标为重算画面。[S8]
- `AReplay::SavePvzState()` 属于回放内部流程，会临时修改出怪和落日相关代码；不要把它当成没有副作用的通用 checkpoint API。
- `AAsm::SaveGame()` 自身也有针对特定小丑状态的修正写入。记录器是否影响目标实验，应通过开启/关闭录制的对照测试确认。[S9]

因此，AReplay 很适合保存失败前一段时间供排查；它不等价于轻量 demo，也不能仅凭有存档就认定包含了完整进程及全部脚本状态。

## 8. 一般 TAS 怎么录制

典型 TAS 的核心文件是**按帧记录的输入序列和环境元数据**。制作时使用逐帧、暂停、读档和输入编辑；完成后回放输入，再导出普通视频。

例如 libTAS 的 `.ltm` 是包含配置、输入及注释等文本文件的压缩包；配置记录游戏哈希、工具版本、初始时间等，输入按帧记录键盘、鼠标、控制器状态。[S10]

Savestate 用于快速跳转和尝试分支。读档后继续录制需要维护输入时间线，不能把被撤销的未来操作继续留在最终有效轨迹中。TASVideos 有专门说明这些规则。[S11]

模拟器能控制大量机器状态，原生 Windows 游戏的控制边界不同。这里借鉴的是 TAS 的记录架构，不表示把一个通用 TAS 工具接上 PvZ 就必然确定性运行。

对 LLM 评测，建议同时保留：

- 最终有效动作轨迹；
- 如果允许回档，全部尝试及 `parent_branch` / `fork_tick` 信息；
- 观察、模型请求与响应、实际执行动作及错误；
- 模拟时间和真实推理耗时分别统计。

只导出成功分支的视频会隐藏尝试次数，不能单独用来衡量策略的无回档成功率。

## 9. 推荐的最小验收顺序

1. 建立统一动作入口和结构化日志，确认所有动作都记录到实际生效的游戏帧。
2. 固定一份初始局面，执行人工写死的动作序列两次；逐帧比较规范化状态摘要，报告首次分叉。
3. 验证从中途检查点恢复后，后续结果是否与连续运行一致。
4. 比较正常推进、暂停后推进、跳帧推进，确认控制方式未改变模拟结果。
5. 比较开启/关闭记录器，确认记录机制没有改变结果。
6. 重启游戏进程后再复跑；不能只在同一进程重复成功就宣布跨运行复现。
7. 前述通过后接入 LLM。重放时使用已记录动作，不重新调用模型。
8. 接入每 4 帧采样的视频流，并核查输出时长是否等于采样覆盖的游戏时间。

状态摘要应排除地址、日志计数等无关变化，保留游戏语义字段和必要的精确浮点信息。只对所选字段做摘要，能证明这些字段一致，不能替代完整状态审计。
