# 雾夜两仪 Python 基准策略

`examples/liangyi_baseline.py` 提供 evaluation 的 `decide(observation, context)` 接口。它是用于实机迭代的状态策略，目标是从官方成型两仪存档完成一个自然两旗周期；**目前没有完成实机通关验收，不能称为稳定解或已证明可挂机策略**。

策略不导入 Client、不读写进程内存、不调用网络或付费模型，也不调用随机数。它只根据输入观察返回 `plant` / `shovel` 动作与需要推进的 tick 数，不修改血量、阳光、冷却、出怪表或波长。原版启动、固定种子、记录、资源隔离和验证仍由 evaluation/launcher/runtime 负责。

## 运行

先用短测确认动作与真实观察一致，再执行完整周期：

```powershell
$env:PYTHONPATH = 'src'
python -m llm_vs_zombies.evaluation plan work/baseline-smoke.json --strategy examples/liangyi_baseline.py
python -m llm_vs_zombies.evaluation run work/baseline-smoke.json --output experiments/runs/baseline-smoke-001

python -m llm_vs_zombies.evaluation plan work/baseline-strict.json --tier strict --strategy examples/liangyi_baseline.py
python -m llm_vs_zombies.evaluation run work/baseline-strict.json --output experiments/runs/baseline-strict-001
```

strict 仍需实际完成两旗、记录完整、逐帧重放、十次冷启动和其他就绪门槛。生成策略文件和离线测试通过不满足这些门槛。若需要只调一个 seed，可编辑生成的计划，例如 `"seeds": [42]`；不能用这一单种子的结果概括整个出怪分布。

## 输入与环境约定

需要当前 runtime 已有的 `version`、`game_ui`、`scene`、`game_clock`、`wave`、`sun`、`plants`、`zombies`、`seeds` 和 `refresh_countdown`。植物至少包含 ID、类型、行列和 HP；僵尸包含 ID、类型、行路、坐标、HP/装甲、状态、速度和冻结/减速剩余时间；卡片包含类型、模仿目标、usable 和 cd_raw。

增强观察会明显提高可靠性：

- `wave_time`：实际波内时刻，按 AvZ 的 `(wave, cs)` 定义。没有该字段时使用首次观察到新波的游戏时钟近似，最大误差约等于前一决策的推进长度；记录中会显示是否使用精确波时钟。
- `plantable["63"][row-1][col-1]` 等：按规范卡类型索引的 6×9 布尔矩阵；63 为模仿冰。也支持每张 seed 内的同名矩阵。它应由真实游戏可种植性判定产生，用来避开核坑和冰道；缺失时策略只能用占格与本地核坑估计，失败后会退避，不能保证有效落地。
- 当前没有巨人动画循环率，因此不实现逐帧铲套躲锤。已有 `state==70` 只用于保守地避免把新垫材塞进正在挥锤的攻击区，不能推导精准命中帧。

阳光采集采用 **固定环境辅助**：runtime 中 AvZ 的自动收集器通过内部游戏调用拾取实际产生的阳光，并以 `source=environment_assist` 记录。策略本身不增加资源。重放必须使用相同构建、同样的收集配置。若该辅助停用，应增加显式可审计的收集策略，不能把“花已产阳光”当作“资源已经入账”。

卡组与参考布局固定：荷叶、南瓜、原冰、模仿冰、核、樱桃、辣椒、倭瓜、小喷、三叶草；4 曾、6 花、2 伞，辅以南瓜和荷叶。永久主植物的 12 个格子都受保护，任何临时灰烬/垫材不会选择这些格子。

## 与官方脚本的关系

调度主要来自固定提交的 [liang_yi.cpp](https://github.com/vector-wlc/AsmVsZombies/blob/c42676c269b5b482a1eb9203a5b979e9d8a2a5c7/tutorial/scripts/liang_yi/liang_yi.cpp)，选位、威胁判断参考 [processor.h](https://github.com/vector-wlc/AsmVsZombies/blob/c42676c269b5b482a1eb9203a5b979e9d8a2a5c7/tutorial/scripts/liang_yi/processor.h) 和 [judge.h](https://github.com/vector-wlc/AsmVsZombies/blob/c42676c269b5b482a1eb9203a5b979e9d8a2a5c7/tutorial/scripts/liang_yi/judge.h)。原作者 vector-wlc 自己就注明演示不能保证成功率、不能直接挂机；Python 版本同样需要实测。

保留的主要结构：

| 项目 | Python 行为 |
|---|---|
| 起手 | 尝试 `(6,9)` 倭瓜，并由下一次实际观察确认 |
| 每波冰 | 480cs 发出用冰调用；模仿冰直接尝试，原冰分支再延迟 320cs |
| 冰交替 | 在用冰调用实际到期时切换，包含第 9/19/20 波额外调用，不简化成奇偶波 |
| 樱桃波 | 1/3/5/7/9/10/12/14/16/18：900cs 分配方向，2200cs 尝试樱桃 |
| 核波 | 2/4/6/8/11/13/15/17/19/20：266cs 尝试辣椒，2200cs 尝试核 |
| 旗帜波 | 第 10 波 295cs 尝试核；第 20 波 295cs 尝试水路樱桃 |
| 收尾 | 第 9 波 2500cs 加辣椒与冰，第 19/20 波 2500cs 加冰 |
| 核位 | 优先尝试官方表，实际不可种时选择合法水路替代格；第 13 波水路与辣椒方向联动 |

与原脚本的明确差异：

1. **不调用 `ASetZombies`**。保持 launcher 提供的真实参考存档/自然出怪环境，不把官方演示的平均出怪表带入实验。
2. 相同的调度意图通过 Python 状态机排队，卡冷却或位置不满足时保留请求继续尝试。提交并不等于成功；只有下一观察出现新植物 ID、真实冷却重置或南瓜 HP 修复才确认消耗卡片。模仿者刚种下尚为 type 48 的转换阶段也会识别。
3. 约 180px 处的气球优先触发三叶草，提供比官方 50px 极限条件更早的余量。已有三叶草时不重复提交。
4. 对危险巨人持续垫小喷，近岸危险时使用倭瓜，紧急时打破固定节奏补原冰/樱桃/辣椒；冰车与已经越过防御线的快怪也有紧急灰烬响应。平静时小喷只预铺岸路四格，不把全场塞满。
5. 巨人的未来忧郁伤害使用官方范围的保守估算，伤害再乘 0.65，降低“看起来会自然死”导致放弃控制的风险。该估计仍未涵盖精确动画、遮挡、对象互动与所有输出离散时间；任一核心缺失时停止使用这项乐观判断。
6. 南瓜按实际损耗修复，岸路曾有更高优先级。若没有 Wall-nut First Aid 导致直接补套不可种，返回“只铲 type 30 南瓜，再种南瓜”的同一批动作，不赠送 First Aid、不铲底下的主植物。它不是精准铲套躲锤技术。
7. 避开正在爆炸的小丑与挥锤/冰车危险落点的判定沿用保守几何近似。没有动画进度时不编造锤击帧或对象栈位优势。
8. 不强制原脚本的全局处理器暂停；只在灰烬生效窗口暂缓一般垫材/重复应急灰烬，紧急气球和修复仍可执行。普通空推进为 20 tick、紧急场景为 1–5 tick；会缩短到下一个已知调度时刻或刷新倒计时。

不同之处都会影响保真度与成功率，不能把此策略标记成“官方脚本逐帧等价移植”。它保留主要冰核节奏，同时通过当前观察选择实际可执行的动作。

## 失败反馈与核坑

若提交失败，策略不会把卡片记为已用、不会乐观删除计划事件。它对相同卡/位置退避 100 tick，并先空推进 1 tick，避免反复失败造成零进度循环。荷叶和水路植物批量操作前，会同时检查两张卡的可用性与合计阳光；若仅荷叶成功，之后可以观察已有荷叶继续尝试主植物。

核坑优先以 runtime 的真实可种植性为准，缺少它时才使用已确认核种植时刻加延迟的保守估计。策略不清除核坑，也不会在周期末重置残留。官方第 20 波核位对下一轮的干扰问题仍需跨周期实测，单次两旗通过不代表连续循环通过。

## 如何验收

离线测试覆盖：气球优先级、资金和推进预算、永久植物保护、只修南瓜层、提交失败不记成功、模仿转换确认、避开真实不可种核位、荷叶合计成本以及额外冰调用改变后续交替。这些都是策略逻辑测试，不是实机胜率证据。

实际测试应保存每波时刻、阳光、确认用卡、失败尝试及 `missing_core` 日志，并同时报告：是否到达下一轮、是否保住 12 格永久主植物、有没有未处理请求、剩余阳光/核坑/冷却。策略每次换波会输出这些诊断摘要；核心一旦缺失，集合会保留该损失。即使游戏最终进入下一次选卡，曾/花/伞的损失也不能从成绩中省略。

推荐先看源实验的动作失败与首次核心损失，修正执行器或策略后再重新冷启动；不要在失败局中补资源、修改数值或删掉失败日志，然后把后半段当作同一次成功实验。最终以 evaluation 产生的真实完整周期与原版重放证据为准。
